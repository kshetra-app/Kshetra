# Poligram Production Readiness Delivery Plan

**Purpose:** Turn the existing mobile app, API, Supabase data layer, and web admin into one dependable political social network and campaign operations platform without replacing working features or presenting simulated activity as real.

**Planning rule:** Keep the existing feature surface. For every domain, first make the current read/write path correct, authenticated, observable, and recoverable; only then expand it. A feature that is not connected to its real provider must say so and remain unavailable for real-world execution.

## Current code facts

- The repository is a monorepo with Expo/React Native (`apps/mobile`), Fastify (`apps/api`), Supabase migrations and Postgres/PostGIS, shared TypeScript contracts, and a Vite admin app (`apps/web-admin`).
- Core social interactions are implemented across API routes, stores, and screens, but not every screen uses the canonical API client or a single persisted source of truth. Some stores make local changes after a failed request and some seed or retain demo records.
- Campaign operations have two generations: legacy routes and mobile stores, and the newer political/commercial campaign domain. They are not yet one consistently durable product path.
- The legacy mobile campaign manager originally contained sample campaign, booth, cadre, ad, revenue, wallet, and delivery data. Its production view is now seeded empty, payment/voice actions fail closed unless confirmed by the service, and audience figures no longer use bundled sample counts. The separate outreach store also used an explicitly mock provider; production now rejects sends and drops simulated delivery history.
- Some API campaign routes use durable Supabase/payment/telecom paths, but real production credentials and end-to-end provider acceptance have not been verified. Campaign reads touched in this tranche no longer substitute in-memory records in production. Other social stores still need a full local-write-on-failure audit.
- The newer commercial and political ad services are process-memory implementations, not durable ad delivery. Their production endpoints now return a clear unavailable response instead of accepting or serving simulated accounts, ads, spend, impressions, clicks, or invoices. Mobile ad-network display remains disabled. These endpoints must be backed by durable tables, verified review, billing, and real delivery before they are re-enabled.
- The web admin previously showed fabricated stream viewers, moderation/civic examples, representative profiles, KYC requests, and infrastructure health. Those examples and simulated admin actions have been removed. Admin sign-in now uses Supabase sessions; civic list and moderation queue screens call their available API routes and only reflect successful writes. The representative, identity-review, and political-ad review screens disclose that their needed persisted queue APIs are not connected.
- Feature-flag reads and writes now use the existing `platform_feature_flags` table in production, and production writes require a verified administrator token. The admin no longer reports offline/default fallback as a successful save. The feature-flag mutation still needs an atomic database audit record and real production migration/role verification before this control should be treated as release-grade.
- Caller-supplied `x-user-id`/`x-user-role` shortcuts and known test admin tokens are now disabled in production on the admin, campaign, civic, politician, page-management, moderation, DM, contributor, and live-broadcast paths touched in this tranche. Production roles for these paths come from verified Supabase identities and server-managed profile data. A complete route-by-route authorization/RLS audit remains outstanding.
- Notification registration, preference, and delivery routes are logging stubs rather than durable token/preferences/provider delivery. They now report unavailable in production instead of returning a successful “dispatched” or “registered” result.
- Some bundled election/reference datasets are intended as offline reference data. They must not be indiscriminately deleted. Each must keep source, date, geographic/election scope, and update/provenance metadata, and must be visually distinguished from live operational metrics.
- Staging remains `IS_STAGING=true` and `IS_PRODUCTION=false` for endpoint/config selection, while the new shared `isProductionLikeEnvironment` policy treats staging/preview and production as deployed environments. The mobile seed, local-write, and unavailable-feature guards in 22 source files now use `IS_LIVE_ENVIRONMENT`; the API's 25 production-gated source files use one `isProductionLikeRuntime` helper. Any production-like marker wins over a conflicting development marker, while isolated `test` mode remains test-only. The admin build now requires explicit API and Supabase environment values and no longer falls back to hard-coded production services. Deployment-variable provisioning and full role/RLS review remain unverified.
- Current ECI materials describe political-ad pre-certification and expenditure-record requirements; Meta describes advertiser authorization, paid-for disclaimers, and its Ad Library for political/social-issue ads. The product needs a maintained compliance workflow and counsel review, not hard-coded claims that one generic flag proves compliance. See [ECI election expenditure monitoring](https://www.eci.gov.in/expenditure-monitoring), [ECI instructions](https://www.eci.gov.in/important-instructions/), and [Meta Ad Library](https://www.facebook.com/ads/library).

## Non-negotiable data and behavior contract

1. Every displayed operational number must come from a named database/provider response or a documented calculation over those records. Keep `source`, `asOf`, scope, and freshness with analytics responses.
2. Unknown is not zero. Render “Not available” or an empty state when data has not loaded; render zero only when the source returned zero for the requested scope.
3. On production API/database failure, return a visible service error or a clearly marked last-known cached result. Never substitute a fixture, local guess, or successful-looking simulation.
4. Fixtures may run only in tests or an explicitly enabled demo build. They cannot be included in a production response or accepted as a real user mutation.
5. Financial and delivery actions are server-authoritative. Wallet credits require a persisted provider order and verified provider callback/signature; ad/voice delivery requires a durable accepted job and provider status. No client-generated payment reference, optimistic credit, timer-based completion, or offline send queue.
6. Treat retries consistently: reads may retry within a bounded policy; non-idempotent writes require idempotency keys and may only be retried when the server can prove safe replay.
7. Keep authenticated user identity and organization/campaign membership server-derived. A client-supplied user, politician, party, role, or campaign ID is a selector to validate, never proof of authority.
8. Political persuasion data is especially sensitive. Start with explicit geographic and contextual delivery, frequency caps, and aggregate reporting. Do not build inferred political-affiliation, caste/religion, or individual “swing voter” targeting. Do not claim privacy compliance until the actual data flows, retention, access, and consent controls have been reviewed.

## Delivery sequence and release gates

## Ten practical product increments

Treat each item as a release-sized vertical slice. Keep the existing route and UI working while the replacement path is added; switch production traffic only after its exit evidence passes. Use additive migrations, compatibility adapters, and feature flags for rollout. Do not delete a working legacy path until traffic, persisted data, rollback, and client compatibility have been verified.

1. **Establish production truth.** Finish the route/store/screen inventory; classify each number as sourced, calculated, cached, fixture, or unknown; remove fixture fallbacks only from production and attach source/freshness to reference data. **Exit:** an empty or failing backend cannot render demo users, campaign results, payments, ad metrics, or successful deliveries.
2. **Make identity and ownership consistent.** Verify session identity on the server; map user → organization/page/campaign once; centralize role and membership checks; test cross-account access. **Exit:** every production read/write has an authorization case and DB ownership policy.
3. **Standardize client/API behavior.** Route calls through the canonical client and shared contracts; align validation, error envelopes, loading/empty/error states, and safe write retry behavior across screens. **Exit:** no screen reports a mutation as saved until the server confirms it; unknown data remains visibly unknown.
4. **Finish social interaction vertical slices.** Choose one surface at a time—post with media, comment/reply, reaction, follow, group membership, or poll—and connect its UI, API, DB policy, notifications, and restart behavior. **Exit:** the action is consistent across feed/profile/group surfaces and survives a new device/session.
5. **Make moderation operable.** Persist reports, evidence references, decisions, moderator identity, appeals, and notices; enforce the same rules in API and UI. **Exit:** a moderator can review an item from durable evidence and the affected user sees an accurate status and appeal route.
6. **Unify campaign operations.** Preserve the existing campaign/booth/cadre models while migrating one action at a time to canonical persisted contracts; add audit history and idempotency to consequential writes. **Exit:** owner and assigned coordinator see the same records across devices, and unsupported dispatch/billing remains explicitly gated.
7. **Complete ad records, review, and transparency.** Continue from the persisted creative-draft slice; add an accountable human review queue, versioned decisions, documented sponsor/disclosure, and a public record before any creative can become eligible. **Exit:** drafts cannot transition to approved/active through a client claim, and every decision has a durable reviewer and timestamp.
8. **Launch in-app ads as a measured first channel.** Start with approved contextual inventory, broad geography, exclusions, opt-outs, frequency caps, a kill switch, and deduplicated impression/click events. **Exit:** serving eligibility is server-side and each reported delivery/spend metric can be recomputed from stored events.
9. **Connect external publishing one provider at a time.** Begin only after the provider account/API approvals and advertiser authorization exist; add server-held credentials, draft/submit/status/pause, and spend reconciliation. **Exit:** the UI reflects provider-confirmed state and unresolved timeouts are checked rather than optimistically reported.
10. **Release with operating evidence.** Add real-baseline SLOs, error and queue alarms, backups/restores, migration rehearsals, staged rollout, support/moderation runbooks, and rollback checks. **Exit:** the team can detect an outage, stop delivery, restore data, and roll back without corrupting financial or social records.

No calendar estimate is asserted here: implementation pace depends on repo work and external production credentials, provider approvals, database state, and operating capacity. Each increment can ship independently when its own exit evidence passes; later ad/provider increments must not block social and campaign improvements that are already supportable.

### Gate 0 — Stop presenting simulations as production activity

**Work:** Gate fixtures and simulations to non-production; remove hard-coded dashboard/audience numbers; make payment and dispatch failures return failure; disable memory-only ad endpoints in production; remove admin example queues and local-only success actions; make API reads return real empty results or service errors instead of sample records. Preserve demo fixtures for developers and verified offline election reference data.

**Exit:** A production build with an empty database shows no example campaign, spend, voter count, ad performance, wallet credit, booth assignment, review item, infrastructure status, notification dispatch, or delivery completion. An API/database outage cannot turn into a success message or fabricated balance. Current work covers the legacy campaign/outreach path, selected campaign API reads/writes, memory-only ad services, notification stubs, admin telemetry and selected review screens, feature-flag persistence/auth, selected API identity fallbacks, and civic issue loading. A repository-wide sweep of all mobile stores, API fallbacks, admin pages, social write paths, authorization claims, RLS policies, and deployment configuration remains required before declaring Gate 0 complete.

### Gate 1 — Establish one application contract and identity boundary

**Work:** Inventory every mobile/web call by feature. Route all calls through the canonical typed API client; define shared request/response/error contracts. Remove hard-coded `pp1`, `c1`, and caller-supplied role assumptions from user-facing operations. Resolve identity, organization membership, permissions, and campaign scope from verified session claims and server-side membership records. Add RLS and ownership checks to each table and endpoint.

**Exit:** Each screen has documented read and write endpoints; every write can be traced to an authenticated principal and resource; API errors/loading/empty/stale states render the same way across clients. Unauthorized cross-account access is rejected by both API policy and database policy.

### Gate 2 — Make social interactions durable and consistent

**Work:** Agree canonical models for person, political page/organization, post, media, follow, group membership, reaction, comment/reply, report, and notification. Close gaps screen by screen: post media upload and attachment, nested replies, group-specific feed/membership rules, entity/page follows, quote/repost attribution, saved items, mentions, and notification preferences. Add transactional outbox/event delivery for notifications so persisted actions and notices cannot drift.

**Exit:** Create/edit/delete/read paths work through the same API and survive restart/device change; permissions and moderation rules match in feed, group, profile, and search surfaces; failed writes do not appear as completed. Ship one capability only after its API, database migration, client, admin controls, and regression coverage land together.

### Gate 3 — Consolidate campaign operations into durable records

**Work:** Select the canonical campaign schema and migrate the other route family behind adapters. Persist campaign, creative, audience definition, approval, spend ledger, wallet, recharge order, delivery job, provider event, volunteer, booth assignment, and audit event in Postgres. Add database constraints, tenant scope, idempotency, event deduplication, and append-only financial records. Replace per-process in-memory service state for any production read/write.

**Exit:** Two API instances return the same campaign/wallet/job state. Payment/order replay cannot duplicate a credit. A campaign read after restart returns only the authenticated owner’s persisted records. Failed persistence blocks delivery and spending.

### Gate 4 — Finish the in-app ad product as a bounded first channel

**Work:** Implement one in-app inventory path: approved campaign creative → server-side eligibility → placement response → impression/click events → aggregate report. Start with contextual placement and broad geography, consent-aware settings, frequency caps, exclusions for sensitive civic/support screens, and clear “Sponsored / Paid for by” identity. Add human review, rejection reasons, appeals, pause/kill switch, and a public transparency record. Define deduplicated event semantics before calculating reach, frequency, CTR, or spend.

**Exit:** An eligible ad can be served only if approved, scheduled, funded, and within caps; each reported metric is reproducible from stored events; user opt-outs and screen exclusions are enforced server-side. Until this passes, keep ad serving disabled and describe the status accurately.

### Gate 5 — Connect external distribution one provider at a time

**Work:** Start only with a provider whose official API and account approvals are available to Poligram. Meta is a possible first connector, not a guaranteed integration: its political-ad authorization and disclaimer requirements must be completed by each advertiser, and provider policy/API access can change. Keep OAuth tokens server-side, least-privileged, encrypted, revocable, and scoped to the connected page/ad account. Implement draft, review, submit, provider status, pause, spend reconciliation, and disconnect. Add additional channels only after the first adapter has stable reconciliation.

**Exit:** The app never says “published” until the provider confirms it; timeouts show “status unknown—checking,” not “failed” or “sent”; provider spend reconciles with Poligram ledger; revocation stops further dispatch. If account approval/API access is unavailable, show the provider as not connected and retain manual export/share where that action is genuinely supported.

### Gate 6 — Trust, safety, and civic integrity operations

**Work:** Define common report/review/appeal workflows, evidence retention, moderator audit trails, impersonation and coordinated-abuse handling, election-period escalation, and correction notices. Make political ad sponsor, approval state, creative versions, targeting rationale, delivery window, and aggregate spend discoverable. Establish public rules against deceptive identity, voter suppression, unverified claims presented as fact, and targeted harassment. Keep synthetic demo identities out of production social graph/search.

**Exit:** Moderators can investigate from durable evidence and record actions; users can appeal; published political ads expose sponsor/disclosure and the review trail appropriate for public transparency. Current legal and platform obligations are rechecked before each market/election launch by qualified counsel and provider review.

### Gate 7 — Operations, reliability, and release discipline

**Work:** Set service SLOs from real baseline measurements; add request IDs, structured logs, traces, queue lag, payment/delivery reconciliation alarms, database health, error budgets, tested backups/restore, migration rollback, incident runbooks, staged rollouts, and mobile crash reporting. Make CI build/type-check/lint and the relevant API, migration, authorization, and UI regression suites required. Use feature flags with owner, expiry, and server-side enforcement.

**Exit:** A release can be rolled back without data corruption; restore is rehearsed; alarms detect failed payment/delivery reconciliation; staged release can be paused; deployment evidence is attached to the release. No target SLO should be invented before collecting production baselines.

Keep the feed, geographic context, polls, Shorts, Live, messaging, and moderation foundations that already exist. Do not accept the audit's numeric strength scores as implementation evidence; a screen or type alone does not prove durable storage, role checks, provider delivery, or production telemetry.

## Political-social product sequence

1. **Inventory and prove the existing path.** For each feed, poll, Shorts, Live, DM, group, and notification action, trace the screen to API, database policy, and stored event. Preserve working flows; mark any local-only or memory fallback as nonproduction.
2. **Stabilize identity and official roles.** Separate account identity from claimed political role and official organization ownership. Verify role claims through server-managed evidence with expiry/revocation and a human review path.
3. **Connect the existing group and geography primitives.** Make group membership, constituency context, and visibility rules server-checked; define how content crosses local/state/national scopes.
4. **Add typed entity follows.** Extend existing follows to resolved representative/page/party/constituency/issue/event/group targets. Store user choices and authorization server-side; use those subscriptions in feed and notification queries.
5. **Make feed behavior explainable.** Return a short reason for a recommendation based on known follow, place, group, or recency signals. Keep a chronological option and user controls.
6. **Close the conversation lifecycle.** Check quote/repost, mentions, nested replies, saved items, and notification preferences against existing routes first; add only missing persistent operations.
7. **Run trust and safety as an operational workflow.** Persist report evidence, moderator decision, appeal, and audit trail. Require human review for high-impact role claims and political ads; use deterministic rate limits and abuse rules before adding more AI calls.
8. **Pilot structured debate and evidence links.** Attach positions, sources, official responses, and nonbinding polls to existing discussion threads. Measure completion and safety outcomes before broad rollout.

This sequence turns the supplied audit's strategic ideas into migrations and API work that fit the current Expo/Fastify/Supabase architecture. It does not assume all listed features are absent; the first step checks whether an existing route or table already provides each one.

## Scope controls and dependencies

- Do not rewrite the mobile app or replace Supabase/Fastify just to make architecture look uniform. Migrate feature-by-feature behind compatible contracts.
- Do not remove verified offline election datasets. Record provenance and validity; remove only data explicitly designated as illustrative or synthetic from production pathways.
- Do not enable real political-ad delivery until advertiser verification, required certifications/disclosures, provider authorization, durable billing, and public transparency have passed their own release gate.
- This repository can implement the application, schemas, adapters, and controls. ## How progress is measured

Track a feature matrix with: UI surface → API route → shared contract → DB table/RLS → provider/event path → authorization case → error/empty behavior → automated regression. A feature is “production ready” only when every column required for that feature is implemented and its release evidence is current. The repo’s build/test pass alone does not prove live credentials, provider approvals, data correctness, or production database state.
