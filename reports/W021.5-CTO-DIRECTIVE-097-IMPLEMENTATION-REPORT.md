## 2. Workstream A — Independently Authenticated Trust Policy

### 2.1 Remediation of Caller Self-Authorization (Rules A & B)
In Directive 096, while trust anchoring was required, callers could supply matching trust pins or whitelist fingerprints in caller-controlled `options`. Under Directive 097, this is strictly eliminated:

1. **Rule A — Prohibit Caller Self-Authorization via Options:**
   A caller cannot authorize its own key by supplying both `options.externalPublicKey` and `options.externalTrustPin` unless established by `process.env.CTO_TRUST_PIN` or explicit isolated test harness authorization:
   ```javascript
   if (callerPublicKey && callerTrustPin && !isIsolatedTest) {
     if (!envTrustPin || envTrustPin.toLowerCase() !== callerTrustPin.trim().toLowerCase()) {
       throw new Error(
         `Ledger accounting validation error: Task ${taskId} formalAcceptanceArtifact "${relPath}" ` +
         `CALLER_SELF_AUTHORIZATION_PROHIBITED: A caller cannot authorize its own key by supplying both ` +
         `externalPublicKey and externalTrustPin in options. The trust pin must be established through the ` +
         `independently trusted configuration boundary (process.env.CTO_TRUST_PIN).`
       );
     }
   }
   ```

2. **Rule B — Prohibit Caller Fingerprint Whitelist Injection:**
   A caller cannot inject a trust policy whitelist in options without independent environment provenance:
   ```javascript
   if (callerTrustPolicy && !isIsolatedTest) {
     if (!envTrustPolicy) {
       throw new Error(
         `Ledger accounting validation error: Task ${taskId} formalAcceptanceArtifact "${relPath}" ` +
         `CALLER_SELF_AUTHORIZATION_PROHIBITED: Caller-supplied trustPolicy cannot establish independent ` +
         `authority without authenticated configuration provenance. Self-authorization via caller-controlled ` +
         `options is prohibited.`
       );
     }
   }
   ```

3. **Production Path Stripping (`validateFormalAcceptanceArtifact`):**

## 3. Workstream B — Truthful & Traceable Test Execution Capture

### 3.1 Test Execution Capture Harness (`scripts/capture_test_execution.mjs`)
The offline test capture runner executes each verification suite using `child_process.spawnSync`, streaming outputs into raw `.log` files in `reports/evidence/test_execution_logs/`, computing SHA-256 digests, and generating `reports/w021_5_test_execution_manifest.json` under schema `v2.0`:

```javascript
export function runSuiteAndCapture(suiteDef) {
  const result = spawnSync(suiteDef.command, {
    cwd: REPO_ROOT,
    shell: true,
    encoding: 'utf8',
    env: { ...process.env, CI: 'true', FORCE_COLOR: '0' },
    maxBuffer: 20 * 1024 * 1024,
  });

  const combinedOutput = (result.stdout || '') + (result.stderr || '');
  const logPath = path.join(LOGS_DIR, suiteDef.logFilename);
  fs.writeFileSync(logPath, combinedOutput, 'utf8');

  const sha256 = crypto.createHash('sha256').update(combinedOutput, 'utf8').digest('hex');
  const { passed, failed, suitesPassed } = parseJestOutput(combinedOutput);

  return {
    suite: suiteDef.suite,
    command: suiteDef.command,
    exitCode: result.status ?? 1,
    status: (result.status === 0 && failed === 0) ? 'PASS' : 'FAIL',
    suitesPassed,
    testsPassed: passed,
    testsFailed: failed,
    durationMs: duration,
    evidenceClass: 'REPOSITORY_IMPLEMENTATION',
    executedInCurrentDelivery: true,
    evidenceType: 'DIRECT_EXECUTION_CAPTURE',
    outputLogPath: relLogPath,
    outputLogSha256: sha256,
  };
}
```
