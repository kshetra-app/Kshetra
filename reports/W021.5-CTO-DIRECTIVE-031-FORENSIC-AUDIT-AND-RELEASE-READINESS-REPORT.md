### 4.2 Database Schema Mechanics & Constraints
1. **`total_assets` Column:**
   - Defined in `008_election_affidavits.sql` (Line 24) as:
     `total_assets BIGINT GENERATED ALWAYS AS (self_movable_assets + self_immovable_assets + spouse_movable_assets + spouse_immovable_assets) STORED`
   - In PostgreSQL, attempting to execute `UPDATE candidate_affidavits SET total_assets = NULL` results in:
     `ERROR: 42601: column "total_assets" can only be updated to DEFAULT`
   - Therefore, direct SQL updates to `total_assets` are mechanically impossible without mutating the underlying component columns (`self_movable_assets`, etc.).
2. **`total_liabilities` Column:**
   - Defined in `008_election_affidavits.sql` (Line 25) as:
     `total_liabilities BIGINT DEFAULT 0`
   - This is an ordinary nullable column. It can be directly updated to `NULL` via standard SQL updates.

### 4.3 Why Package A1 Was Retained for Ingestion (The Operational Rationale)
In Directive 024, Chunk 02 was already executed on staging using Package A1 semantics (where omitted liabilities defaulted to 0 and component assets were 0). If Chunks 03–05 had introduced `NULL` for liabilities while Chunk 02 remained `0`, the staging database would be in a fractured state with inconsistent default semantics across state batches.

Retaining Package A1 for base ingestion guarantees:
1. All four SQL chunks share identical column mapping and value coercion rules.
2. Checkpoints 03–08 and the Consolidated Gate evaluate clean, homogenous data structures without unexpected null-pointer exceptions in arithmetic expressions.
3. Base population execution reaches clean closure without runtime constraint errors.
