### 1.2 Syntax and Semantics of `DROP EXPRESSION`
- **Engine Support:**
  The SQL command `ALTER TABLE [table] ALTER COLUMN [column] DROP EXPRESSION [ IF EXISTS ]` was introduced in **PostgreSQL 12.0** and is standard, fully supported functionality across PostgreSQL 12, 13, 14, 15, 16, and 17.
- **DDL Command Specification:**
  ```sql
  ALTER TABLE public.candidate_affidavits
    ALTER COLUMN total_assets DROP EXPRESSION IF EXISTS;
  ```
- **Internal PostgreSQL Catalog Semantics:**
  1. Modifies `pg_attribute.attgenerated` for `total_assets`, changing it from `'s'` (stored generated) to `''` (ordinary base column).
  2. Drops the internal expression record from `pg_attrdef`.
  3. **Preserves existing stored heap data:** It does *not* zero out, drop, or alter existing values stored on disk in `candidate_affidavits.total_assets`.
  4. Leaves column nullability intact (`is_nullable = 'YES'`, as declared in [`supabase/migrations/008_election_affidavits.sql`](file:///c:/Users/Laven/OneDrive/Desktop/Kshetra/supabase/migrations/008_election_affidavits.sql#L24-L26)).
  5. Converts `total_assets` into an ordinary stored `BIGINT` column capable of receiving direct `UPDATE` values, including explicit `NULL`s.

## 4. Fail-Closed Snapshot and Recovery Design

### 4.1 Rejection of Unsafe `IF NOT EXISTS` Reuse
- **Defect in Prior Proposal:** Using `CREATE TABLE IF NOT EXISTS public._w021_5_candidate_affidavits_pre067_snapshot AS SELECT *` is unsafe because if a stale or corrupted table already exists from an aborted run or prior experiment, the statement silently skips creation, and the migration proceeds against stale snapshot data.
- **Fail-Closed Pre-Execution Check:**
  The migration must refuse to run if the snapshot table already exists:
  ```sql
  DO $$
  BEGIN
    IF EXISTS (
      SELECT 1 FROM information_schema.tables 
      WHERE table_schema = 'public' 
        AND table_name = '_w021_5_candidate_affidavits_pre067_snapshot'
    ) THEN
      RAISE EXCEPTION 'PRE_EXISTING_SNAPSHOT_DETECTED: Table public._w021_5_candidate_affidavits_pre067_snapshot already exists. Refusing to execute to prevent stale data reuse.';
    END IF;
  END $$;
  ```

### 4.2 Snapshot Creation and Immediate Pre-Execution Validation
Once confirmed absent, the snapshot is created and validated within the same transaction:
```sql
CREATE TABLE public._w021_5_candidate_affidavits_pre067_snapshot AS 
SELECT * FROM public.candidate_affidavits;

DO $$
DECLARE
  v_snap_count INT;
  v_live_count INT;
  v_dup_count  INT;
BEGIN
  SELECT count(*) INTO v_snap_count FROM public._w021_5_candidate_affidavits_pre067_snapshot;
  SELECT count(*) INTO v_live_count FROM public.candidate_affidavits;
  SELECT count(*) - count(DISTINCT id) INTO v_dup_count FROM public._w021_5_candidate_affidavits_pre067_snapshot;

  IF v_snap_count <> 4523 THEN
    RAISE EXCEPTION 'SNAPSHOT_VALIDATION_FAILED: Snapshot row count (%) does not equal 4523.', v_snap_count;
  END IF;

  IF v_snap_count <> v_live_count THEN
    RAISE EXCEPTION 'SNAPSHOT_VALIDATION_FAILED: Snapshot count (%) does not match live table count (%).', v_snap_count, v_live_count;
  END IF;

  IF v_dup_count <> 0 THEN
    RAISE EXCEPTION 'SNAPSHOT_VALIDATION_FAILED: Snapshot contains % duplicate IDs.', v_dup_count;
  END IF;
END $$;
```

### 4.3 Transaction Failure and Forward Recovery Architecture
- **Atomic Transaction Enclosure:**
  The entire remediation script will execute inside a single transactional block (`BEGIN; ... COMMIT;`). If any SQL error, lock timeout, or invariant exception triggers, PostgreSQL rolls back all modifications automatically, leaving the live table in its exact pre-migration state.
- **Rejection of Destructive Generated-Column Rollback:**
  - A naive rollback that attempts to re-create the generated column (`GENERATED ALWAYS AS (...) STORED`) would require dropping the restored `total_assets` values or recalculating them from the 4 component columns. Because the component columns were omitted during original ingestion and remain 0, re-generating the column would immediately re-collapse all 4,340 restored asset values back to 0.
- **Deterministic Forward-Recovery Procedure:**
  1. In the event of a post-commit issue, schema rollback is strictly prohibited.
  2. The table structure remains normalized (`total_assets` as ordinary `BIGINT`).
  3. Live rows are restored directly from `public._w021_5_candidate_affidavits_pre067_snapshot` via primary key join:
     ```sql
     UPDATE public.candidate_affidavits a
     SET 
       total_assets = s.total_assets,
       total_liabilities = s.total_liabilities,
       updated_at = s.updated_at
     FROM public._w021_5_candidate_affidavits_pre067_snapshot s
     WHERE a.id = s.id;
     ```
  4. Post-recovery verification verifies bitwise parity against the pre-execution snapshot.
