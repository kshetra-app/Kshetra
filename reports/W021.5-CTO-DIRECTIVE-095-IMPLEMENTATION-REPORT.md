## 2. Workstream A — Independent Trust Boundary Architecture

### 2.1 Circular Trust Elimination
In prior implementations, the trust anchor was loaded from `governance/authorities/cto_root_public_key.pem` within the workspace repository. An actor with repository write access could generate a rogue Ed25519 keypair, commit the public key to `governance/authorities/cto_root_public_key.pem`, and self-sign acceptance records.

Directive 095 eliminates this vulnerability by enforcing an **external trust boundary**:
1. Authority keys stored in the repository are considered **untrusted proposals** until pinned by an external trust pin.
2. The reconciler (`scripts/reconcile_execution_ledger.mjs`) computes the SHA-256 fingerprint of the repository key:
   ```javascript
   export function computeKeyFingerprint(keyBuffer) {
     return crypto.createHash('sha256').update(keyBuffer).digest('hex');
   }
   ```
3. To validate an acceptance record, the reconciler requires either:
   - `options.externalTrustPin` or `process.env.CTO_TRUST_PIN` matching the SHA-256 fingerprint of the key, OR
   - `options.externalPublicKey` directly providing the external PEM string.
4. If no external trust pin or key is provided, the validator throws `TRUST_ANCHOR_UNPINNED` and fails closed.
5. If the provided pin does not match the key fingerprint, the validator throws `TRUST_PIN_MISMATCH` and fails closed.

### 2.2 Canonical Payload Serialization & Signer Requirements
Acceptance records are verified using Ed25519 digital signatures computed over a strictly deterministic canonical JSON payload:
```javascript
export function getCanonicalAcceptancePayload(record) {
  return JSON.stringify({
    milestone: record.milestone,
    taskRef: record.taskRef,
    decision: record.decision,
    adjudicatorIdentity: record.adjudicatorIdentity,
    adjudicatorRole: record.adjudicatorRole,
    adjudicationDate: record.adjudicationDate,
    authorSelfAcceptance: record.authorSelfAcceptance,
    conditions: record.conditions || [],
    findings: record.findings || [],
  });
}
```

In addition to cryptographic signature validity, the reconciler enforces:
- `keyId`: must resolve to an active, non-revoked entry in `governance/authorities/trusted_authorities.json`.
- `role`: authority entry must declare `role === 'CTO'`, and record must declare `adjudicatorRole === 'CTO'`.
- `identity`: record must match registered authority identity (`Kshetra Chief Technology Officer`).
- `algorithm`: must strictly be `'Ed25519'`.
- `status`: authority entry must be `'ACTIVE'` (`status !== 'REVOKED'`).
- `validityWindow`: timestamp of adjudication must fall between `validFrom` and `validUntil`.
- `authorSelfAcceptance`: strictly `false` (violating this throws `RULE_IV_001_VIOLATION`).

## 3. Workstream B — Enforceable Acceptance Criteria and Executable Verifiers

### 3.1 Architecture of `TASK_SPECIFICATIONS`
In `scripts/reconcile_execution_ledger.mjs`, all 27 tasks are configured with explicit, testable criteria and executable verifiers. Each task defines:
- `title`: canonical task title.
- `stage`: canonical milestone stage (`STAGE_A` through `STAGE_I`).
- `weight`: task weight $W_i$.
- `deliverables`: list of concrete file paths required in the repository.
- `criteria`: array of criteria objects, each having `id`, `description`, `weight`, and `verifier(task, options)`.
- `repoVerifiedWeight`, `databasePendingWeight`, `blockedWeight`, `unimplementedWeight`: non-overlapping weight components satisfying $W_i = \sum W$.

### 3.2 Dynamic Ratio Derivation
Rather than hardcoding arbitrary `repoRatio` values, `evaluateTaskAcceptanceCriteria(task, options)` executes every verifier:
$$\text{derivedRepoRatio} = \frac{\sum_{\text{passed}} \text{criterion.weight}}{\sum_{\text{all}} \text{criterion.weight}}$$

The reconciler enforces fail-closed consistency:
1. Every task must define at least one acceptance criterion.
2. Every criterion must have an executable verifier function.
3. Every verifier must execute and return a boolean pass/fail with inspection details.
4. If any criterion fails or is unexecuted, `derivedRepoRatio` drops proportionately.
5. If a task's earned weight does not match $\text{weight} \times \text{derivedRepoRatio}$, the reconciler throws `DERIVED_RATIO_MISMATCH`.

## 4. Workstream C — Non-Overlapping Progress Model

### 4.1 Flaw in Prior Subtractive Model
Directive 094 computed:
$$\text{Repository Readiness} = 64.0\%, \quad \text{DB Discount} = 13.0\%, \quad \text{Earned Completion} = 51.0\%$$
This formulation had a fundamental defect: it allowed database-pending work to overlap with earned progress, creating ambiguity regarding whether the discount was being subtracted from completed repository work or from incomplete work.

### 4.2 Mutually Exclusive Partition Formulation
Directive 095 establishes a strict mathematical partition for every task $i \in \{1, \dots, 27\}$:
$$W_i = \text{repoVerifiedWeight}_i + \text{databasePendingWeight}_i + \text{blockedWeight}_i + \text{unimplementedWeight}_i$$
where:
- $\text{repoVerifiedWeight}_i$: Deliverables and criteria fully implemented and verified in the repository ($61.5\%$).
- $\text{databasePendingWeight}_i$: Code/data delivered in repository but awaiting live database execution ($10.5\%$).
- $\text{blockedWeight}_i$: Work blocked on external human decisions, CTO adjudication, or infrastructure ($22.5\%$).
- $\text{unimplementedWeight}_i$: Work scheduled for subsequent phases not yet authored ($5.5\%$).

### 4.3 Conservation Law and Reconciliation Metrics
Summing over all 27 tasks yields:
$$\sum_{i=1}^{27} \text{repoVerifiedWeight}_i = 61.5\%$$
$$\sum_{i=1}^{27} \text{databasePendingWeight}_i = 10.5\%$$
$$\sum_{i=1}^{27} \text{blockedWeight}_i = 22.5\%$$
$$\sum_{i=1}^{27} \text{unimplementedWeight}_i = 5.5\%$$

$$\mathbf{61.5\% + 10.5\% + 22.5\% + 5.5\% = 100.0\%}$$

Supplementary dimensions:
- **Live Database Staging Execution:** Strictly **0.0%** (zero migrations run, zero mutations performed).
- **Formal CTO Acceptance:** Strictly **0.0%** (strictly unaccepted under Rule IV-001).

## 5. Workstream D — Hardened Semantic Artifact Validation

### 5.1 SQL Statement Parser (`validateSqlContent()`)
The previous SQL validator failed on complex migrations containing dollar-quoted procedural blocks (`$$ ... $$` or `$body$ ... $body$`).

The hardened SQL validator in Directive 095 implements:
1. **Comment Stripping:** Safely strips single-line (`--`) and multi-line (`/* ... */`) comments while respecting string literals.
2. **Quote & Dollar-Quote Depth Tracking:** Tracks quote states (`'`, `"`, `` ` ``) and custom dollar-quote tags (`$[a-zA-Z0-9_]*\$`). Parentheses and semicolon boundaries are only evaluated outside quoted and dollar-quoted regions.
3. **Statement Recognition:** Validates that remaining tokens form valid SQL statements starting with recognized DDL/DML keywords (`CREATE`, `ALTER`, `INSERT`, `UPDATE`, `DELETE`, `DROP`, `GRANT`, `BEGIN`, `COMMIT`, etc.).
4. **Adversarial Hardening:** Rejects comment-only files, keyword-only strings lacking statement structure, and files with unbalanced syntax. Tested against all 68 SQL migrations with 100% pass rate.

### 5.2 TypeScript AST Test Parser (`validateTestContent()`)
The previous test validator relied on simple substring matching, which could admit token-only files containing inert words like `test` or `describe` in variable names or comments.

The hardened test validator implements syntax analysis:
1. Strips comments and string literals.
2. Scans for executable call expressions (`CallExpression`) representing test framework invocations (`test(`, `it(`, `describe(`, `runTest(`, `suite(`).
3. Verifies assertion invocations (`assert.`, `expect(`, `should.`).
4. Rejects token-only files that contain test keywords without executable invocations.

### 5.3 GeoJSON Boundary Validator (`validateGeoJsonContent()`)
Validates geographic datasets (`data/geo/telangana-assembly.geojson`):
1. Verifies JSON parsing and root type (`Feature` or `FeatureCollection`).
2. Rejects empty feature collections (`features: []`).
3. Validates geometry types (`Polygon`, `MultiPolygon`, `Point`, `LineString`).
4. Validates coordinates are finite numbers within the Indian sovereign bounding box:
   $$\text{Longitude: } 60.0^\circ \text{ to } 105.0^\circ, \quad \text{Latitude: } 4.0^\circ \text{ to } 42.0^\circ$$
5. Verifies linear rings are closed (first coordinate exactly equals last coordinate).
6. Detects and reports duplicate AC IDs (e.g., the duplicate AC 119 claim in Telangana), cleanly separating syntactic correctness from statutory completeness.

### 5.4 Markdown and JSON Validators
- **Markdown:** Enforces structured headings (`#`, `##`), minimum 200 characters of meaningful content, and domain-relevant vocabulary.
- **JSON:** Enforces strict schema parsing and rejects empty objects (`{}`) or empty arrays (`[]`).
