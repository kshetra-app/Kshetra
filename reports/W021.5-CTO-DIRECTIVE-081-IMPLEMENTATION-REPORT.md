## 1. Executive Summary & Objective

CTO Directive 081 addresses the durability-reporting gap identified in Directive 080: in `scripts/generate_checksum_manifest.mjs`, the initial implementation of directory synchronization after atomic rename silently swallowed all errors using an unqualified `catch (_) {}` block. This introduced the risk of reporting full unqualified success when directory-entry durability was uncertain, and failed to distinguish documented, platform-specific unsupported operations from genuine I/O or filesystem errors.

Directive 081 resolves this gap by:
1. **Distinguishing Unsupported Operations from Genuine I/O Errors:** Formally categorizing recognized unsupported operations (`EINVAL`, `ENOTSUP`, `EOPNOTSUPP`, `EISDIR`, `EPERM`, `EBADF`, and Win32 directory handle limitations) from genuine filesystem errors (`EIO`, `ENOSPC`, `EROFS`, `EDQUOT`, `EBUSY`, `EACCES`, etc.).
2. **Implementing `PostRenameDurabilityError`:** Introducing a distinct error class indicating that the atomic replacement has already succeeded and the new manifest is installed on disk, but directory-entry durability could not be confirmed to stable storage.
3. **Prohibiting False Invariance Claims:** Explicitly ensuring that error reporting does not falsely claim the original manifest remains intact when rename has already succeeded.
4. **Suppressing Unqualified Success Banners on Failure:** Ensuring that `MANIFEST GENERATION: 100% COMPLETE` is never emitted when directory durability confirmation fails with a genuine error.
5. **Preserving Pre-Rename Guarantees & Anti-Rollback Safety:** Retaining complete byte-for-byte preservation and temp-file cleanup for pre-rename failures, while strictly avoiding destructive rollback or deletion of the newly installed manifest on post-rename durability errors.
6. **Expanding the Regression Battery:** Expanding `scripts/tests/generate_checksum_manifest.test.mjs` from 18 to 26 automated regression tests, covering all post-rename durability paths, fault injection modes, and platform behaviors.
7. **Hardening Mechanical Accounting:** Updating `scripts/audit_artifact_accounting.mjs` with Category O (`O_DIRECTIVE_081`), reconciling total deliverables to 53 across 15 categories, and verifying git provenance coordinates for Directive 080.

## 2. Technical Architecture & Implementation Details

### 2.1 Post-Rename Directory Synchronization & Durability Model

In modern file systems, atomic file replacement using temporary files requires two distinct durability phases:
1. **File Data & Inode Durability:** Flushing file content blocks and inode metadata to stable storage using `fsync(fd)`.
2. **Directory Entry Durability:** Flushing the parent directory's block/inode mapping to ensure the directory entry update survives an immediate crash or power loss.

On POSIX systems, directory synchronization is performed by opening the directory file descriptor (`fs.openSync(dirPath, 'r')`) and executing `fs.fsyncSync(dirFd)`. However, filesystems and operating systems exhibit significant architectural diversity:

| Platform / Filesystem | Directory `fsync` Support | Behavior / Error Code | Classification |
| :--- | :--- | :--- | :--- |
| **Linux (ext4, xfs, btrfs)** | Supported | Flushes directory entry to disk journal/blocks | Supported & Synced |
| **Network Filesystems (NFS, SMB)** | Frequently Unsupported | Returns `EINVAL` or `ENOTSUP` | Recognized Unsupported Operation (Non-Fatal) |
| **FAT32 / exFAT / RAMFS** | Unsupported | Returns `EINVAL`, `ENOTSUP`, or `EISDIR` | Recognized Unsupported Operation (Non-Fatal) |
| **Restricted Containers / Sandboxes** | Restricted | Returns `EPERM` or `EBADF` | Recognized Unsupported Operation (Non-Fatal) |
| **Windows / NTFS (libuv / Win32)** | Unsupported on directory handles | `FlushFileBuffers` requires write access; returns `EINVAL`/`EPERM` | Recognized Platform Limitation (Non-Fatal; relies on NTFS `$LogFile` / `$MFT` transaction log) |
| **Physical Disk Fault / Bad Sectors** | Hardware Failure | Returns `EIO` | **Genuine I/O Error** (`PostRenameDurabilityError`) |
| **Filesystem Out of Space / Quota** | Storage Depleted | Returns `ENOSPC` or `EDQUOT` | **Genuine Filesystem Error** (`PostRenameDurabilityError`) |
| **Read-Only Filesystem Remount** | Filesystem Remounted RO | Returns `EROFS` | **Genuine Filesystem Error** (`PostRenameDurabilityError`) |

### 2.2 Error Handling & Durability Classification

In `scripts/generate_checksum_manifest.mjs`, `UNSUPPORTED_DIR_SYNC_CODES` defines the authoritative set of non-fatal unsupported codes:
```javascript
export const UNSUPPORTED_DIR_SYNC_CODES = new Set([
  'EINVAL',     // Invalid argument (common on Linux/FreeBSD when fs does not support dir fsync)
  'ENOTSUP',    // Operation not supported
  'EOPNOTSUPP', // Operation not supported on transport endpoint
  'EISDIR',     // Is a directory (rejected by platforms where fsync is regular-file only)
  'EPERM',      // Operation not permitted (sandbox policy or Win32 FlushFileBuffers on directory)
  'EBADF'       // Bad file descriptor
]);
```

When a directory synchronization error occurs:
- If `err.code` is present in `UNSUPPORTED_DIR_SYNC_CODES`, the error is recorded as non-fatal, the durability status is set to `UNSUPPORTED_OPERATION_${err.code}`, and the operation proceeds to completion.
- If the error is NOT in `UNSUPPORTED_DIR_SYNC_CODES`, it represents a genuine I/O or filesystem failure. The function throws `PostRenameDurabilityError`:

```javascript
export class PostRenameDurabilityError extends Error {
  constructor(targetPath, tempPath, cause) {
    const causeMsg = cause ? (cause.message || String(cause)) : 'Unknown error';
    const causeCode = cause && cause.code ? ` [code: ${cause.code}]` : '';
    super(
      `POST_RENAME_DURABILITY_ERROR: Directory synchronization failed after successful atomic rename${causeCode}. ` +
      `The new manifest may already be installed at ${targetPath}, but directory-entry persistence durability could not be confirmed ` +
      `to stable storage. NOTE: The previous manifest was replaced and is no longer intact: ${causeMsg}`
    );
    this.name = 'PostRenameDurabilityError';
    this.code = 'POST_RENAME_DURABILITY_ERROR';
    this.isPostRename = true;
    this.renameSucceeded = true;
    this.targetPath = targetPath;
    this.tempPath = tempPath;
    this.cause = cause;
  }
}
```

### 2.3 Anti-Rollback & Preserved Replacement Guarantee

A critical invariant enforced by Directive 081 is that **rename is a point of no return**:
- Prior to rename (`renameSucceeded === false`), any failure unlinks the temporary file and guarantees that the target manifest remains untouched byte-for-byte.
- After rename (`renameSucceeded === true`), the target manifest already contains the fully written, file-fsynced content. An attempt to "rollback" or delete the target would destroy valid data and introduce corruption. Therefore, `atomicWriteFileSync` never unlinks `targetPath` on post-rename errors.
- The error message explicitly clarifies to the caller and operators that the previous manifest was replaced, preventing false assumptions of prior-state invariance.
