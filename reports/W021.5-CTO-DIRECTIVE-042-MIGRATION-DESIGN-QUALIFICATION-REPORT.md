### 2.3 Lock Level, Transaction Boundary, and Operational Risk
- **DDL Lock Level:**
  Executing `ALTER TABLE candidate_affidavits ALTER COLUMN total_assets DROP EXPRESSION` acquires an `ACCESS EXCLUSIVE` lock on `public.candidate_affidavits`.
  - *Duration:* Because the column was already physically materialized as `STORED`, PostgreSQL does **not** rewrite the table heap or recompute rows. It performs an in-memory catalog update (`pg_attribute.attgenerated = ''`), which completes in **< 10 milliseconds**.
  - *Concurrency Impact:* Reads and writes are blocked for the duration of the catalog update.
- **Batch Update Lock Level:**
  The subsequent data updates on 4,412 rows acquire `ROW EXCLUSIVE` locks on the targeted rows and fire the `BEFORE UPDATE` trigger (`trg_affidavit_updated_at`) 4,412 times.
  - *Duration:* In PostgreSQL, updating 4,412 rows in a 4,523-row table (table size ~1.8 MB) takes **50–150 milliseconds**.
- **Transaction Boundary:**
  All operations (the DDL expression drop, the batch updates, and the provenance update) must be wrapped inside a single atomic transaction block (`BEGIN; ... COMMIT;`).
- **Operational Risk Verdict:**
  Total transaction execution duration will be approximately **100–200 milliseconds**. While blast radius on staging is zero (offline environment), live production will experience a brief ~150ms write lock. The claim of "zero downtime" is qualified: it requires a brief, sub-second exclusive lock window.

## 5. Workstream D — Honest Recovery and Rollback Strategy

### 5.1 Why Naive DDL Rollback Destroys Source Truth
A traditional rollback that attempts to restore the schema by re-adding the generated column expression:
```sql
-- DANGEROUS / DESTRUCTIVE ROLLBACK
ALTER TABLE candidate_affidavits DROP COLUMN total_assets;
ALTER TABLE candidate_affidavits ADD COLUMN total_assets BIGINT GENERATED ALWAYS AS (...) STORED;
```
is **strictly rejected**:
1. Dropping `total_assets` destroys all 4,340 restored non-zero totals.
2. When re-added, the generated expression evaluates the component columns. Because component columns are `NULL` or `0`, `total_assets` instantly collapses back to `0` or `NULL`, re-corrupting the entire financial database.
3. A structural rollback that destroys financial truth is not a recovery; it is a re-introduction of the defect.

### 5.2 Tested Forward-Recovery & Safety Strategy
1. **Pre-Execution Physical Snapshot:**
   Within the migration script prior to DDL normalization, create an isolated staging snapshot table:
   ```sql
   CREATE TABLE IF NOT EXISTS public._w021_5_candidate_affidavits_pre067_snapshot AS
   SELECT * FROM public.candidate_affidavits;
   ```
   This captures the exact bitwise state of all 4,523 rows as deployed by Chunks 02–05.
2. **Atomic Single-Transaction Execution:**
   The entire Migration 067 file (snapshot creation, DDL normalization, and keyed updates) executes inside a single PostgreSQL transaction (`BEGIN; ... COMMIT;`). Any syntax error, constraint failure, or timeout triggers an automatic, engine-level `ROLLBACK` that leaves the table completely untouched.
3. **Deterministic Forward Recovery:**
   If post-migration verification identifies an anomaly in a specific chunk or state, recovery is performed via forward-patching from the immutable snapshot or manifest CTE:
   ```sql
   UPDATE public.candidate_affidavits c
   SET total_assets = s.total_assets,
       total_liabilities = s.total_liabilities
   FROM public._w021_5_candidate_affidavits_pre067_snapshot s
   WHERE c.id = s.id AND c.state_code = '<affected_state>';
   ```
4. **Post-Acceptance Snapshot Cleanup:**
   The snapshot table `_w021_5_candidate_affidavits_pre067_snapshot` remains preserved in Staging until the CTO formally executes and certifies Checkpoint 067 as `PASS`.
