## 4. Validation of Proposed Update Semantics

### 4.1 PostgreSQL Schema Architecture (`008_election_affidavits.sql`)
```sql
CREATE TABLE public.candidate_affidavits (
  ...
  self_movable_assets BIGINT DEFAULT 0,
  self_immovable_assets BIGINT DEFAULT 0,
  spouse_movable_assets BIGINT DEFAULT 0,
  spouse_immovable_assets BIGINT DEFAULT 0,
  total_assets BIGINT GENERATED ALWAYS AS (
    self_movable_assets + self_immovable_assets + spouse_movable_assets + spouse_immovable_assets
  ) STORED,
  total_liabilities BIGINT DEFAULT 0,
  ...
);
```

### 4.2 Mathematical & Engine Update Behaviors
1. **Generated Column Invariant:** Direct update on `total_assets` (`UPDATE ... SET total_assets = NULL`) is physically forbidden by PostgreSQL and throws:
   `ERROR: 42601: cannot insert/update into generated column "total_assets"`.
2. **Null Propagation Mechanism:** In SQL standard arithmetic, `NULL + ... = NULL`. Because the generation expression does not use `COALESCE`, updating the 4 component columns:
   ```sql
   UPDATE public.candidate_affidavits
   SET self_movable_assets = NULL,
       self_immovable_assets = NULL,
       spouse_movable_assets = NULL,
       spouse_immovable_assets = NULL
   WHERE id = '<target_id>';
   ```
   causes PostgreSQL's stored generated column engine to evaluate `NULL + NULL + NULL + NULL` and store `NULL` in `total_assets`. No DDL alterations or table re-creations are required.
3. **Liability Update Mechanism:** `total_liabilities` is a nullable column (`BIGINT DEFAULT 0`). Direct update:
   ```sql
   UPDATE public.candidate_affidavits
   SET total_liabilities = NULL
   WHERE id = '<target_id>';
   ```
   evaluates cleanly without schema modification.
4. **Targeted Row Integrity:**
   - Population remains invariant at exactly 4,523 rows.
   - Zero rows added, zero rows deleted.
   - All primary key UUIDs, foreign keys, and natural key constraints remain unchanged.
