## 2. Workstream A — Fail-Closed Test Capture Engine

### 2.1 Vulnerability Audit of Previous Implementation
In previous implementations (`capture_test_execution.mjs`), test output parsing relied on non-negative default counts:
- If a runner exited with code 0 but emitted unrecognized output, `parseJestOutput()` or custom summary regexes failed to match, defaulting `failed` count to 0 and `passed` count to 0.
- A process exiting with code 0 could be treated as `PASS` even when no test discovery occurred or test output was malformed.
- Exit code 0 was accepted without requiring positive evidence that the intended test suite actually executed.

### 2.2 Re-Architected Fail-Closed Parser (`parseTestOutput`)
In Directive 098, `scripts/capture_test_execution.mjs` was re-engineered with strict fail-closed classification:

```javascript
export function parseTestOutput(rawOutput, suiteDef = {}) {
  // 1. Guard against empty or whitespace-only output
  if (!rawOutput || !rawOutput.trim()) {
    return { isParsed: false, failureReason: 'EMPTY_OUTPUT', passed: 0, failed: 0, totalTests: 0, ... };
  }

  // 2. Guard against runner discovering zero tests (line-anchored detection)
  if (/^(?:No tests found|No test files found|Zero tests executed|No tests discovered|Ran 0 test suites)\b/im.test(rawOutput)) {
    return { isParsed: false, failureReason: 'NO_TESTS_DISCOVERED', passed: 0, failed: 0, totalTests: 0, ... };
  }

  // 3. Positive Suite Identity Verification
  // Binds output to expected suite basename, stripped name, or directive number
  if (!isExpectedSuitePresent(rawOutput, suiteDef)) {
    return { isParsed: false, failureReason: 'SUITE_IDENTITY_MISMATCH', passed: 0, failed: 0, totalTests: 0, ... };
  }

  // 4. Custom Summary Parser (VERIFICATION SUMMARY: X PASSED, Y FAILED)
  // 5. Jest Output Parser (Tests: X passed, Y failed, Z total)
  // ...
  // If neither format matches:
  return { isParsed: false, failureReason: 'UNPARSED_OUTPUT_FORMAT', passed: 0, failed: 0, totalTests: 0, ... };
}
```

### 2.3 Discrete Execution & Parse Outcomes
The capture engine distinguishes 7 mutually exclusive execution outcomes:
1. `EMPTY_OUTPUT`: Process produced empty or whitespace-only output.
2. `NO_TESTS_DISCOVERED`: Process runner reported zero test files or zero discovered tests.
3. `UNPARSED_OUTPUT_FORMAT`: Output format could not be parsed into recognized test metrics.
4. `ZERO_TESTS_PASSED`: Process reported 0 passed tests.
5. `SUITE_IDENTITY_MISMATCH`: Executed output did not contain positive evidence matching the expected suite identity.
6. `TESTS_FAILED`: Executed suite reported one or more failing tests.
7. `PROCESS_EXIT_NON_ZERO`: Process terminated with a non-zero exit code or spawn error.

### 2.4 Positive Suite Identity Binding
To ensure a different test suite cannot satisfy a manifest entry, `isExpectedSuitePresent(rawOutput, suiteDef)` validates that stdout contains:
- The exact suite path (e.g. `tests/political-intelligence-directive-098.test.mjs`), OR
- The suite basename (e.g. `political-intelligence-directive-098.test.mjs`), OR
- The stripped test name (e.g. `political-intelligence-directive-098`), OR
- The directive reference header (e.g. `DIRECTIVE 098` or `DIRECTIVE 98`).

### 2.5 Deterministic Log Structure & Incremental Manifest Integrity
Logs are written to `reports/evidence/test_execution_logs/<name>.log` with a strict deterministic format:
```
================================================================================
KSHETRA VERIFIABLE TEST EXECUTION LOG
Suite: <suite path>
Command: <executed command>
Working Directory: <cwd>
Runtime: Node <version> (<platform>)
Execution Timestamp: <ISO-8601>
Exit Code: <exit code>
================================================================================

--- STDOUT ---
<verbatim stdout>

--- STDERR ---
<verbatim stderr>

--- PROCESS METRICS ---
DurationMs: <duration>
ExitCode: <exit code>
================================================================================
```
The SHA-256 digest is computed over the complete log content and recorded in `reports/w021_5_test_execution_manifest.json`.

`validateManifestIntegrity(manifest, repoRoot)` verifies:
- Manifest schema and milestone (`W021.5`).
- Uniqueness of test suites (no duplicate entries).
- Execution scope and epoch declarations (`DIRECTIVE_098`).
- Existence of all referenced log files on disk.
- Bitwise SHA-256 match between disk log files and manifest records.
- Binding between log header and manifest suite path.
- Exact arithmetic agreement between suite test counts and summary totals.

## 5. Workstream D — Independent Trust Boundary Assurance

### 5.1 External Provisioning Architecture
Under Master Execution Framework Amendment v1.2 / Rule IV-001, operationally independent trust cannot be established by repository-committed keys or caller-controlled options alone.
- **Independent Anchor Provisioning:** The Chief Technology Officer provisions trust outside caller control via `process.env.CTO_TRUST_PIN` (a 64-character lowercase hex SHA-256 digest of the trusted public key) or `process.env.CTO_TRUST_POLICY` (specifying approved fingerprints, algorithms, and minimum key length).
- **No Self-Authorization:** A caller cannot establish authority by passing public keys, certificates, fingerprints, or trust pins in caller options.
- **Fail-Closed Default:** In the offline repository environment without external CTO environment provisioning, formal acceptance is strictly unavailable (`0.0%`).

### 5.2 Protection of Canonical Production Tasks
In `scripts/reconcile_execution_ledger.mjs`, `validateFormalAcceptanceArtifact()` strictly enforces:
```javascript
const isCanonicalTask = !task || !task.taskId || !task.taskId.startsWith('W021.5-TEST-') || TASK_SPECIFICATIONS[task.taskId];
const effectiveOptions = { ...options };

if (isCanonicalTask) {
  // Canonical production tasks STRICTLY strip all caller override and bypass options
  delete effectiveOptions.isolatedTestHarnessAuth;
  delete effectiveOptions.testHarnessIsolatedAuth;
  delete effectiveOptions.externalTrustPin;
  delete effectiveOptions.trustPolicy;
  delete effectiveOptions.trustedAuthorities;
  delete effectiveOptions.externalPublicKey;
  delete effectiveOptions.syntheticTask;
  delete effectiveOptions.isSyntheticTask;
}
```
This guarantees that callers cannot pass `syntheticTask: true` on canonical production tasks (`W021.5-A-01` through `W021.5-I-01`) to bypass trust stripping.
