## 1. Executive Mission & Objective

This register performs a rigorous, evidence-based audit mapping the real, observable implementation of the Kshetra platform against the 10 core architectural domains of Milestone W021.5.

Its purpose is **not** to claim completion of W021.5. Its purpose is to clearly distinguish:
- What is **canonical** (source of truth, validated, stable contract).
- What is **adapter-based** (bridging between disparate local shapes).
- What is **seed-only** (offline local repository fixtures in `data/seed/`).
- What is **partial, duplicated, or absent**.
- Specific gaps, migration risks, and architectural anomalies in `DATA_ARCHITECTURE.md`.

## 2. Comprehensive Domain Audit (10 Core Areas)

### Domain 1: Canonical Jurisdiction & Constituency Identity Registry
- **Existing Files / APIs / Models:**
  - `data/seed/*-constituencies.ts` (31 files, 4,123 statutory assembly records).
  - `apps/api/src/services/stateData.ts` (`STATE_RAW_MAP`, `getConstituencies`, `getConstituency`).
  - `apps/api/src/routes/constituencies.ts` (`GET /states/:stateCode/constituencies`, `GET /states/:stateCode/constituencies/:id`).
  - `@kshetra/shared`: `ConstituencyBrief` contract (`id`, `name`, `acNo`, `stateCode`, `district`, `reservationStatus`, `currentParty`, `currentMLA`).
  - `supabase/w021_5_staging_master_migration_package_050_066.sql` (`constituencies` table, `DL-AC-001` to `DL-AC-070`).
- **Current Capability Classification:** `ADAPTER_BASED / SEED_ONLY`
- **Concrete Evidence:**
  - The runtime Fastify API routes and mobile app do NOT query a live central database registry; they dynamically read local TypeScript arrays (`data/seed/*-constituencies.ts`).
  - IDs follow the format `{STATE}-AC-{acNo}` (e.g. `TS-AC-65`), but are constructed at runtime in adapters rather than retrieved from an immutable database primary key with lineage tracking.
  - Delhi statutory seats are strictly 70, yet demographic seed files (`delhi-demographics.ts`) include 151 non-assembly entries (`DL-AC-071` to `DL-AC-221`).
- **Dependencies & Consumers:** Mobile search, state directory, routing (`/constituency/[id]`), API detail endpoint.
- **Data Migration & Compatibility Risks:** Promoting seed identities to an immutable SQL registry requires reconciling demographic placeholders without breaking client routes.
- **Recommended Next Stage & Prerequisites:** Stage W021.5-G1: Database-Backed Canonical Constituency Registry. Prerequisite: Staging schema verification and demographic separation.

### Domain 2: Canonical Person & Political-Organization Identity/Deduplication
- **Existing Files / APIs / Models:**
  - `data/seed/*-mla-profiles.ts` (31 files).
  - `apps/mobile/stores/affidavits.ts` (28 candidate records).
  - `apps/api/src/services/stateData.ts` (`getMLAProfile`).
  - `apps/api/src/routes/constituencies.ts` (`GET /states/:stateCode/mla/:acNo`).
- **Current Capability Classification:** `SEED_ONLY / PARTIAL`
- **Concrete Evidence:**
  - Candidates and representatives lack a global canonical Person ID (e.g. `PERSON_IND_...`). MLA IDs are synthesized on-the-fly via string concatenation (e.g. `MLA_TS_2023_Kodangal_65` or `MLA_TS_65`).
  - If a politician contests across multiple constituencies (e.g. KCR contesting Gajwel and Kamareddy), they exist as separate, disconnected profile records without a common person entity.
  - Political parties are stored as plain strings (e.g. `'INC'`, `'BRS'`, `'BJP'`), with no canonical political party registry entity.
- **Dependencies & Consumers:** `LegislatorProfileScreen`, `CandidateAvatar`, candidate search, MLACard.
- **Data Migration & Compatibility Risks:** Introducing canonical Person IDs requires migrating all route parameters from composite string slugs to UUIDs or unique canonical slugs while maintaining backward compatibility.
- **Recommended Next Stage & Prerequisites:** Stage W021.5-G2: Person & Entity Deduplication Service. Prerequisite: Cross-election candidate graph construction.

### Domain 3: Terms, Office Holdings, Party Affiliations, Vacancies & Current-Truth Resolution
- **Existing Files / APIs / Models:**
  - `data/seed/*-political-timeline.ts`.
  - `data/seed/telangana-mla-profiles.ts` (`defectionHistory`, `terms`).
  - `apps/api/src/services/stateData.ts` (manual by-election overrides for confirmed October 2026 by-elections in TN, WB, PY).
  - `apps/mobile/components/DefectionBadge.tsx`, `DefectionJourneyCard.tsx`.
- **Current Capability Classification:** `PARTIAL / ADAPTER_BASED`
- **Concrete Evidence:**
  - Current-truth is resolved by checking recent election winners with manual by-election override logic hardcoded in `stateData.ts` (e.g. TN AC#35 TVK, TN AC#101 TVK, WB AC#210 BJP, WB AC#70 BJP, PY AC#9 AINRC).
  - Vacancies, disqualifications, and mid-term defections are not modeled as formal temporal state-machine events in a database.
- **Dependencies & Consumers:** `ConstituencyBrief.currentMLA`, `ConstituencyBrief.currentParty`, `ProfileHeroCard`.
- **Data Migration & Compatibility Risks:** Hardcoded override logic in API service will drift as real-world legislative changes occur unless backed by an event-sourced ledger.
- **Recommended Next Stage & Prerequisites:** Stage W021.5-G3: Legislative Office Holding & Defection Temporal Ledger. Prerequisite: Domain 1 & 2 completion.

### Domain 4: Per-Election Results, Source Provenance, Verification & Correction History
- **Existing Files / APIs / Models:**
  - `apps/api/src/services/stateData.ts` (`getConstituencyElectionData`).
  - `apps/api/src/routes/constituencies.ts` (`recentElection`, `elections[]`).
  - `data/seed/*-historical-results.ts` (Present in 8 states: TS, AP, KA, MH, TN, KL, WB, UP; Absent in 23 states).
  - `reports/w021_5_national_data_coverage_matrix.json`.
- **Current Capability Classification:** `PARTIAL / SEED_ONLY`
- **Concrete Evidence:**
  - Only 8 of 31 states have per-constituency historical election records. 23 states have only the single recent assembly election.
  - Margin percent and votes are preserved truthfully without zero coercion (`number | null`), and unknown election years remain `null`.
  - However, records are static TypeScript objects without cryptographic provenance hashes, ingestion batch IDs, or correction history audit logs.
- **Dependencies & Consumers:** `ConstituencyDetailDTO.recentElection`, `ConstituencyDetailDTO.elections`, mobile History tab.
- **Data Migration & Compatibility Risks:** Ingestion of comprehensive historical results for the 23 unseeded states requires automated schema validation to prevent malformed vote counts.
- **Recommended Next Stage & Prerequisites:** Stage W021.5-G4: National Multi-Election Historical Results Repository. Prerequisite: ECI Form 20/21E structured data extraction.

### Domain 5: Data Ingestion, Source Freshness, Update Monitoring & Event Propagation
- **Existing Files / APIs / Models:**
  - `DATA_ARCHITECTURE.md` (claims automated 8-layer scraper architecture, `pg_cron` daily export, etc.).
- **Current Capability Classification:** `ABSENT IN RUNTIME (DOCUMENTED SPEC ONLY)`
- **Concrete Evidence:**
  - No active scraper daemon, queue worker (BullMQ/RabbitMQ), or pg_cron job exists in the committed repository runtime.
  - All data is checked in as static `.ts` files in `data/seed/`.
  - There is zero automated delta ingestion, webhook notification, or cache invalidation pipeline.
- **Dependencies & Consumers:** All mobile and API consumer paths.
- **Data Migration & Compatibility Risks:** High architectural debt if consumers assume real-time data freshness while underlying records remain static fixtures.
- **Recommended Next Stage & Prerequisites:** Stage W021.5-G5: Asynchronous Ingestion & Verification Pipeline. Prerequisite: Secure credential boundary and schema isolation.

## 3. Critical Audit of `DATA_ARCHITECTURE.md`

A line-by-line inspection of `DATA_ARCHITECTURE.md` against the actual repository revealed several severe discrepancies, obsolete claims, and unsafe source guidance that must be flagged:

1. **"Zero Empty Fields Strategy" vs Data Truthfulness:**
   - *Claim:* "Fill 100% of LegislatorProfile fields for every MLA, MP... No field is left without a source."
   - *Audit Finding:* This design principle directly violates W021.5 data truthfulness rules. In W021.5, missing, undisclosed, or unverified data MUST remain `null` or explicit Pending Notices. Forcing 100% completion encourages fabricated zeroes and inferred placeholders.
2. **Unsafe Data Inferences:**
   - *Claim (Section 1.1):* "Caste: ECI constituency reservation status -> ECI master list"; "DOB: MyNeta age + election date (estimate)"; "Gender: Indian names gender DB (95% accuracy) + MyNeta photo visual ML".
   - *Audit Finding:* Inferring an individual's caste from their constituency's reservation status or estimating DOB and gender via name heuristics is legally, ethically, and computationally unsafe for a political intelligence platform. These heuristics must be excised.
3. **Ghost Infrastructure Claims:**
   - *Claim (Section 2.1 & 3.1):* 8-layer scraper hierarchy running in production, `pg_cron daily export` into static JSON snapshots, OTA daily sync.
   - *Audit Finding:* Zero scrapers exist in the operational API runtime. No `pg_cron` pipeline runs daily exports. All data currently originates from static local `.ts` seed files in `data/seed/`.
4. **Redundant Dual Storage:**
   - *Claim (Section 3.1):* Three-tier storage (PostgreSQL -> Static JSON -> AsyncStorage).
   - *Audit Finding:* In reality, the mobile app bundles the static `.ts` files directly, with Fastify reading the same seed files. A true production strangler pattern requires the API to serve database records while the mobile client caches responses in MMKV/AsyncStorage without bundling raw national seeds.
