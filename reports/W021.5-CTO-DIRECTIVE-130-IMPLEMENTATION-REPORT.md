## 1. Executive Summary & Purpose

CTO Directive 130 executes a focused repository-side validation and reporting correction addressing the remaining defects identified in the independent audit of Directive 129. In strict adherence to Master Execution Framework Amendment v1.6 and Rule IV-001, this directive establishes exact locator-extent validation, enforces a single source-resolution chain, strengthens multi-AC candidate validation, corrects the 38-scenario negative test battery to test actual validator/parser mechanisms, classifies evidence across 12 orthogonal dimensions, and guarantees Stage B report and gate integrity.

Key achievements under Directive 130:
1. **Exact Locator and Administrative Extent Validation across All 36 Records:**
   - Every single record is checked against the parsed source extract from disk.
   - Known discrepancies explicitly reconciled:
     * PIN `500053`: Former locator claimed `GHMC Ward 15 part`. Cited Chandrayangutta (AC 67) source entry specifies `Ward No. 16 to 18`. Both `sourceLocator` and `whatSourceEstablishes` now cite and verify `Ward No. 16 to 18`.

   - Validator (`CHECK_7`) strictly enforces that `sourceLocator` contains `sourceEntry.extent` for single-AC and all candidate entries for multi-AC.
2. **One Enforced Source-Resolution Chain:**
   - The validation chain is strictly:
     `declared source path -> resolved file -> live SHA-256 -> parsed entry -> extracted passage -> locator verification -> claim-support verification`.
   - The validator parses the exact declared file on disk rather than selecting a file by `stateCode`.
   - Manifest entries declaring a path discordant with the expected state/schedule are rejected.
   - Negative test (Scenario 28) proves that a wrong-state or wrong-schedule file with a matching checksum is rejected.
   - Checksum verification proves identity against recorded digest; it is decoupled from official publication authenticity and transcription fidelity.
3. **Strengthened Multi-AC Candidate Verification:**
   - For all 4 multi-AC records (`500001`, `500028`, `500034`, `500056`), every candidate AC number, candidate name, and candidate administrative extent is resolved and verified against the parsed source extract.
   - Asserts $\ge 2$ candidates, zero duplicate candidate numbers, and canonical `assignedAcNumber === undefined` (fail-closed).
   - Strictly separates statutory entry text from manually authored postal delivery beat descriptions.
4. **Corrected 38-Scenario Negative-Test Battery:**
   - All 38 scenarios execute real validator, parser, and generator mechanisms with specific check ID assertions.
   - Scenarios test exact locator extent mismatches (Scenario 27), cross-state source bindings (Scenario 28), altered disk artifacts with live hash checks (Scenario 32), multi-AC candidate mismatches (Scenario 34), unsupported postal assertions (Scenario 35), Markdown generator failure retention (Scenario 37), and report generator anti-override guards (Scenario 38).
5. **12 Orthogonal Evidence Dimensions:**

   - Evaluates separate Conclusion A (Identity) vs Conclusion B (Postal Linkage).
7. **Actual Report and Gate Integrity:**

   - Enforces `evidenceClosureStatus !== 'COMPLETE'` while statutory gazettes and India Post GIS delivery beat boundary polygons remain external and uninspected.
