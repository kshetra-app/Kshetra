## 6. Schema Feasibility Analysis Without Schema Changes (§6)

Under Directive 071 Section 6, an offline design analysis was performed using the committed schema ([`supabase/migrations/008_election_affidavits.sql`](file:///c:/Users/Laven/OneDrive/Desktop/Kshetra/supabase/migrations/008_election_affidavits.sql)) and consumer code:

### 6.1 Limitations of the Existing Generated Column
In `008_election_affidavits.sql` (lines 38–45):
```sql
  self_movable_assets BIGINT DEFAULT 0,
  self_immovable_assets BIGINT DEFAULT 0,
  spouse_movable_assets BIGINT DEFAULT 0,
  spouse_immovable_assets BIGINT DEFAULT 0,
  total_assets BIGINT GENERATED ALWAYS AS (
    self_movable_assets + self_immovable_assets + spouse_movable_assets + spouse_immovable_assets
  ) STORED,
```
1. **Inability to Represent Disclosed Totals Without Breakdown:**
   In 26 jurisdictions (3,403 affidavits), Form 26 filings only provide `totalAssets`. Under SQL mechanics, if components are `NULL`, the expression `NULL + NULL + NULL + NULL` yields `NULL`, obliterating the disclosed total. If components are left `0`, the expression evaluates to `0`, producing false zeros.
2. **Prohibition of Direct Insertion/Update:**
   In PostgreSQL, a `GENERATED ALWAYS` column cannot be updated directly (`ERROR: 42601`).
3. **Violation of Zero Fabrication:**
   The only workaround under the current schema without DDL alteration is "Component Attribution" (e.g. setting `self_movable_assets = total_assets` and immovable = 0). This violates the Zero Fabrication Rule by falsely asserting that 100% of candidate assets are movable property.

### 6.2 Feasibility of Converting `total_assets` to a Stored Column (Method A)
Converting `total_assets` from a generated column to a regular stored column (via `ALTER TABLE candidate_affidavits ALTER COLUMN total_assets DROP EXPRESSION IF EXISTS`) with nullable components (`BIGINT NULL`) enables faithful, simultaneous representation of all five mandatory states:

1. **State 1 (Disclosed positive total with no breakdown):**
   `total_assets = 521356863`, components = `NULL`.
   *Consumer:* `FinancialBreakdownCard` renders ₹52.14 Cr total, displays "Not Disclosed" for components, and suppresses the stacked bar chart.
2. **State 2 (Undisclosed total / Missing disclosure):**
   `total_assets = NULL`, components = `NULL`.
   *Consumer:* Renders "Not Disclosed", net worth computation remains `null`, crorepati ratio excludes row from disclosed denominator.
3. **State 3 (Genuine zero total):**
   `total_assets = 0`, components = `0` (or `NULL` if only total disclosed).
   *Consumer:* Renders ₹0, net worth computed as $0 - \text{liabilities}$, red flag flags genuine zero debt vs unknown debt.
4. **State 4 (Positive total with partial breakdown):**
   `total_assets = 1000000`, `self_movable = 600000`, other components = `NULL`.
   *Consumer:* Renders total, renders disclosed components, labels absent ones "Not Disclosed", suppresses stacked bar.
5. **State 5 (Positive total with complete breakdown):**
   `total_assets = 1000000`, components sum to `1000000`.
   *Consumer:* Renders total, all 4 breakdown items, and renders complete stacked bar chart.

### 6.3 Unverified Assumptions Due to Air-Gap
1. **Production PostgreSQL Engine Version:** PostgreSQL 15.x is standard on modern Supabase, where `ALTER COLUMN ... DROP EXPRESSION IF EXISTS` is supported (introduced in PostgreSQL 12). However, because production Supabase (`ehfafcnimmjusyvplbah`) is strictly air-gapped, `SELECT version()` has not been run directly on production.
2. **Transaction Concurrency & Table Locks:** `ALTER COLUMN ... DROP EXPRESSION` acquires an `ACCESS EXCLUSIVE` lock on `candidate_affidavits`. While metadata-only and fast for 4,523 rows, live connection pooling and timeout thresholds must be confirmed prior to execution.
3. **Dependent Schema Objects:** Whether any views, triggers, or indexes in the database catalog directly depend on `total_assets` remains unverified against live catalogs.

### 6.4 Migration Risks and Rollback Considerations
- **Risk 1 (Component Default Coercion):** If DDL drops the expression but leaves `DEFAULT 0` on component columns, future inserts might re-introduce false zero components. The migration must alter component column defaults to `NULL`.
- **Risk 2 (Backfill Race Window):** Dropping the expression preserves the existing stored value (currently `0`). A separate batch update must immediately backfill authoritative positive values and `NULL`s before client traffic resumes.
- **Rollback Consideration:** `DROP EXPRESSION` cannot be rolled back with a simple ALTER without re-evaluating the expression across all rows. Rollback requires pre-taking a logical table backup or PITR snapshot.
