## 2. Workstream A — Independent Trust Boundary & Cryptographic Adjudication

### 2.1 Closing the Trust-Anchor Bypass
In Directive 095, `verifyCryptographicAcceptanceSignature()` allowed callers to supply `options.trustedAuthorities` directly. A test runner or malicious caller could inject an arbitrary authority registry containing their own public key without anchoring it to an external trust source.

In Directive 096, this bypass has been closed. An external trust anchor is **unconditionally mandatory**:
```javascript
// From scripts/reconcile_execution_ledger.mjs
const externalTrustPin = options.externalTrustPin || process.env.CTO_TRUST_PIN;
const trustPolicy = options.trustPolicy || (process.env.CTO_TRUST_POLICY ? JSON.parse(process.env.CTO_TRUST_POLICY) : null);

if (!externalTrustPin && !trustPolicy) {
  throw new Error(
    `Ledger accounting validation error: Task ${taskRef} formalAcceptanceArtifact "${artifactPath}" TRUST_ANCHOR_UNPINNED. ` +
    `No external trust pin (process.env.CTO_TRUST_PIN or options.externalTrustPin) or approved external trust policy was provisioned. ` +
    `Repository-committed keys and caller-supplied registries cannot establish their own authority without an independent trust anchor.`
  );
}
```

### 2.2 Enforcing Explicit Trust Modes
The reconciler now supports two explicit, mutually exclusive trust policy modes:

1. **`PIN_ANCHORED` Mode:**
   - Requires `options.externalTrustPin` or `process.env.CTO_TRUST_PIN`.
   - The pin must be a valid 64-character lowercase hex string representing the SHA-256 digest of the canonical public key.
   - The public key fingerprint is computed over normalized line endings:
     $$\text{fingerprint} = \text{SHA-256}(\text{publicKeyPem.replace(/\r?\n/g, '\n').trim()})$$
   - If the computed fingerprint does not match the external trust pin, verification fails closed with `TRUST_PIN_MISMATCH`.

2. **`APPROVED_FINGERPRINTS` Mode:**
   - Requires `options.trustPolicy = { mode: 'APPROVED_FINGERPRINTS', approvedFingerprints: [...] }`.
   - The key fingerprint must explicitly exist in the caller-supplied `approvedFingerprints` whitelist.
   - If the key fingerprint is not approved, verification fails closed with `TRUST_POLICY_MISMATCH`.

3. **External Public Key Policy (`options.externalPublicKey`):**
   - Supplying `options.externalPublicKey` alone without an anchoring policy fails closed with `UNTRUSTED_EXTERNAL_KEY`.

### 2.3 Comprehensive Decision Field Binding
The cryptographic signature is verified against a canonical JSON payload that strictly binds all decision-relevant fields:
```javascript
export function getCanonicalAcceptancePayload(record) {
  return JSON.stringify({
    milestone: record.milestone,
    taskRef: record.taskRef,
    decision: record.decision,
    adjudicatorIdentity: record.adjudicatorIdentity,
    adjudicatorRole: record.adjudicatorRole,
    adjudicationDate: record.adjudicationDate,
    authorSelfAcceptance: record.authorSelfAcceptance,
    conditions: record.conditions || [],
    findings: record.findings || [],
  });
}
```
Tampering with any of the following fields immediately invalidates the signature:
- `keyId`: Signer key ID mismatch or unregistered key.
- `adjudicationDate`: Modifying the timestamp invalidates the signature and enforces the authority's `[validFrom, validUntil]` validity window.
- `taskRef`: Modifying the task reference prevents replaying acceptance across tasks.
- `decision`: Changing decision (e.g. `REJECTED` to `ACCEPTED`) invalidates the signature.
- `conditions`: Adding, removing, or modifying conditions invalidates the signature.
- `findings`: Modifying findings invalidates the signature.
- `authorSelfAcceptance`: Setting `authorSelfAcceptance: true` strictly fails closed under Rule IV-001 (`RULE_IV_001_VIOLATION`), even if the signature is valid.

### 2.4 Removal of Wrapper Bypasses
All four-argument signature functions (`verifyCryptographicAcceptanceSignature(record, artifactPath, options, authorities)`) and internal wrappers were unified to call the same verification logic. No alternative verification path exists.

## 5. Workstream D — Semantic Validation & Test Execution Proof

### 5.1 Hardened SQL Parser
`scripts/reconcile_execution_ledger.mjs` implements `stripSqlCommentsAndLiterals()`:
1. Strips line comments (`-- ...`) and block comments (`/* ... */`).
2. Identifies dollar-quoted string literals (`$$...$$` and `$tag$...$tag$`) and replaces their content with whitespace to prevent keywords inside strings from being counted as SQL statements.
3. Identifies single-quoted and double-quoted strings and tracks quote depth to detect unclosed string literals.
4. Verifies statement delimiters (`;`) and presence of valid DDL/DML verbs (`CREATE`, `ALTER`, `DROP`, `INSERT`, `UPDATE`, `DELETE`, `GRANT`, `REVOKE`, `SELECT`).

### 5.2 TypeScript AST Test Parser
`validateTestContent()` parses TypeScript source files using the official TypeScript compiler API (`ts.createSourceFile`):
1. Traverses the AST for `CallExpression` nodes.
2. Identifies test runner functions: `describe`, `it`, `test`, `suite`, `runTest`.
3. Identifies assertion expressions: `assert`, `expect`, `.assert`, `.expect`.
4. Rejects token-only files (keywords in strings/comments) and comment-only test files.

### 5.3 Test Execution Manifest Verification
For tasks that require test passage (e.g. `W021.5-G-02`, `W021.5-H-01`), the criteria verifiers cross-reference `reports/w021_5_test_execution_manifest.json`:
