## 3. P0: Asymmetric Cryptographic Authorization Architecture

### 3.1 Asymmetric Verification Contract (`scripts/lib/stagingAuthorization.mjs`)

The legacy symmetric HMAC implementation has been completely removed from the production path. The authorization verifier now enforces a true public-key cryptographic contract:

1. **Algorithm Allowlist:** Restricted strictly to `Ed25519` and `RS256`. Symmetric algorithms (`HS256`, `HS384`, `HS512`) and `none` are unconditionally rejected (`ERR_DISALLOWED_ALGORITHM`).
2. **Public-Key Only Operation:** The verifier imports trust anchors via `crypto.createPublicKey()`. Public keys are strictly checked to ensure they are not HMAC secrets or private keys. The verifier contains zero signing capabilities.
3. **Isolated Test Helpers:** Token signing capabilities exist strictly in [`tests/helpers/stagingAuthTestHelper.mjs`](file:///c:/Users/Laven/OneDrive/Desktop/Kshetra/tests/helpers/stagingAuthTestHelper.mjs) for testing purposes using ephemeral test key pairs.
4. **Public-Key Forgery Proof:** An adversarial test explicitly proves that a holder of the verifier's public key cannot forge a valid authorization token without the governance private key.
5. **Fail-Closed Trust Anchor Loading:** If `KSHETRA_CTO_PUBLIC_KEY` is unset and the public key file (`governance/keys/cto_staging_auth_public.pem`) is absent, the verifier fails closed with `ERR_TRUST_ANCHOR_UNAVAILABLE`.

### 3.2 Bound Authorization Claims

Every staging authorization token must be cryptographically bound to the following claims:

- `iss`: Authorized governance authority (`kshetra-governance-cto`).
- `aud`: Authorized audience (`kshetra-staging-executor`).
- `stagingProjectRef`: Exact Supabase staging project reference (`fkpigozcqnmcvofuksar`).
- `authId` & `jti`: Unique authorization ID and one-time token identifier.
- `iat`, `nbf`, `exp`: Strict temporal window. Expiry must not exceed `maxLifetimeSeconds` (86,400s / 24h).
- `allowedCriteria`: Exact array of approved criteria (`CRIT-C02-02`, `CRIT-D02-02`, `CRIT-E01-02`, `CRIT-F02-03`).
- `allowedTables`: Explicit target tables. Write operations outside approved tables fail closed.
- `allowedOperations`: Prohibited from specifying `DELETE`, `DROP`, or `TRUNCATE`.
- `executionPlanDigest`: SHA-256 digest of the reviewed execution plan payload. Mismatched digests are rejected.
- `adminIncidentClosureRef`: Administrative incident reference confirming staging credential rotation.

### 3.3 Concurrency-Safe Durable Anti-Replay Store (`scripts/lib/stagingReplayStore.mjs`)

Process-local in-memory `Set` collections have been replaced by a durable, disk-backed anti-replay store:

- **Atomic Reservation:** Atomically checks and reserves tokens before execution begins.
- **Cross-Process Mutual Exclusion:** Uses directory/file locking (`.lock`) with stale-lock detection and atomic temp-file renaming.
- **Process Restart Persistence:** Replay state persists across process restarts. An adversarial multi-process test verifies that independent child processes cannot replay a reserved nonce.
- **Fail-Closed Availability:** If the replay store directory is unwritable or unavailable, the system fails closed with `REPLAY_STORE_UNAVAILABLE` before any network or database operation can occur.

## 7. P1: Timestamp Anomaly Root Cause & Resolution

The apparent future timestamp in the Directive 141 defect ledger (`2026-10-22T23:45:00.000Z`) was audited and resolved:

- **Root Cause:** The developer machine operates in Indian Standard Time (IST, UTC+05:30). During Directive 141 documentation generation, the local wall-clock time was 23:45 IST. The timestamp string was erroneously authored with a literal `Z` (UTC) suffix instead of being converted to UTC ($23:45 \text{ IST} = 18:15 \text{ UTC}$).
- **Resolution:** All generation scripts, verification runners, ledgers, and reports now strictly utilize runtime dynamic `new Date().toISOString()`, completely eliminating manual timezone conversions.
