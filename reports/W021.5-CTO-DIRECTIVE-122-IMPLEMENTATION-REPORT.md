## 2. WORKSTREAM A — DELIMITATION POSTAL DATA-TRUTH REMEDIATION (`DEF-W021-05`)

### 2.1 The Legacy Data-Truth Problem
Prior to Directive 122, `apps/api/src/services/delimitationService.ts` contained a critical electoral data-truth defect:
1. It maintained a sparse collection of 3-digit PIN prefixes (`PIN_PREFIX_MAPPING`).
2. When a PIN matched a prefix, it selected an Assembly Constituency using modulo arithmetic on the PIN suffix:
   ```typescript
   // LEGACY DEFECTIVE LOGIC:
   const acIndex = pinSuffix % stateConstituencies.length;
   const currentAC = stateConstituencies[acIndex];
   ```
3. If no state constituencies existed in the seed data, it generated a synthetic assembly constituency record:
   ```typescript
   // LEGACY FABRICATION:
   const currentAC = {
     acNo: (pinSuffix % 70) + 1,
     name: `${stateData.district} North`,
     district: stateData.district,
     totalVoters: 250000 + (pinSuffix % 50000),
     reservation: 'GEN' as const,
     incumbentParty: 'INC',
     incumbentMLA: 'Current MLA'
   };
   ```
4. It derived simulated boundary changes, voter retention percentages, and proposed constituency splits based on this arbitrary assignment.
5. While Directive 121 eliminated the silent fallback to Telangana for unmapped PINs (introducing fail-closed 404 `PIN_NOT_FOUND`), the arbitrary modulo assignment remained active for all mapped prefixes.

### 2.2 Domain Realities of Indian Postal Geography
A 3-digit Indian PIN prefix identifies a broad postal division or sorting district (e.g., prefix `110` covers the entire National Capital Territory of Delhi spanning 70 Assembly Constituencies; prefix `400` covers the Mumbai postal region spanning dozens of constituencies across two revenue districts).
- A PIN code does **NOT** establish a 1:1 authoritative statutory relationship with an Assembly Constituency.
- Modulo arithmetic on PIN suffixes produces arbitrary hallucinations that vary with unrelated postal delivery beats.
- Postal prefixes cannot be treated as statutory delimitation boundaries.

### 2.3 Implementation of the Remediation Architecture

#### 2.3.1 Shared Contract Refactoring (`packages/shared/src/contracts/delimitation.ts`)
The `CitizenImpactDTO` contract was refactored to support honest non-assignment, regional-level reporting, and candidate ambiguity:
```typescript
export interface CitizenImpactDTO {
  pinCode: string;
  stateCode: string;
  stateName: string;
  district: string;
  region: string;
  coverageLevel: 'POSTAL_ZONE_REGION' | 'CURATED_PROVISIONAL_POINT' | 'AUTHORITATIVE_STATUTORY';
  linkageNotice: string;
  candidateConstituencies?: Array<{
    acNo: number;
    name: string;
    district: string;
    reservation: 'GEN' | 'SC' | 'ST';
  }>;
  currentConstituency?: {
    acNo: number;
    name: string;
    district: string;
    totalVoters: number;
    reservation: 'GEN' | 'SC' | 'ST';
    incumbentParty?: string;
    incumbentMLA?: string;
  };
  proposedConstituency?: {
    proposedAcNo: number;
    proposedName: string;
    projectedVoters: number;
    reservation: 'GEN' | 'SC' | 'ST';
    changeType: 'RETAINED' | 'MODIFIED' | 'NEW_SEAT' | 'MERGED';
  };
  impactAnalysis?: {
    status: 'SPLIT' | 'RETAINED_IN_CORE' | 'TRANSFERRED' | 'AMBIGUOUS_CANDIDATES';
    voterRetentionPct?: number;
    reservationStatusChanged?: boolean;
    explanation: string;
    isScenarioEstimate?: boolean;
    spatialCaveat?: string;
  };
}
```

#### 2.3.2 Elimination of Modulo Arithmetic and Synthetic Records (`apps/api/src/services/delimitationService.ts`)
1. **Zero Modulo Arithmetic:** All occurrences of `pinSuffix % ...` were completely eradicated.
2. **Zero Synthetic Constituencies:** Removed all synthetic fallback generators producing fabricated MLAs (`'Current MLA'`), parties (`'INC'`), and seat names (`'${district} North'`).
3. **Directory Classification:** Explicitly classified `PIN_PREFIX_MAPPING` as `POSTAL_DIRECTORY_CLASSIFICATION = 'APPROXIMATE_REGIONAL_CLASSIFICATION'`.
4. **Curated Provisional Reference Directory:** Introduced `CURATED_PROVISIONAL_PIN_DIRECTORY` covering verified urban reference points (Hyderabad/Secunderabad and AP urban core) where an unambiguous reference constituency can be provided provisionally with explicit scenario flags.

#### 2.3.3 The Four Statutory Lookup Cases
- **Case A — Unmapped PIN (Fail-Closed):**
  - Syntactically invalid PIN (not 6 digits): returns 400 `FST_ERR_VALIDATION`.
  - Unmapped PIN (e.g., `999999`): fails closed with 404 `PIN_NOT_FOUND` (`"PIN code 999999 is not mapped to any known postal zone"`).
- **Case B / Section 3.4 — Generic Regional Prefix (Ambiguity Preserved):**
  - When a PIN maps to a broad regional prefix (e.g., `110001` Delhi, `400001` Mumbai, `560001` Bengaluru):
    - Returns regional information (`stateCode`, `stateName`, `district`, `region`, `coverageLevel: 'POSTAL_ZONE_REGION'`).
    - Strictly sets `currentConstituency: undefined`, `proposedConstituency: undefined`, `impactAnalysis: undefined`.
    - Populates `candidateConstituencies` with canonical seats in that district/state and sets `impactAnalysis.status: 'AMBIGUOUS_CANDIDATES'`.
    - Issues `linkageNotice: "Postal code corresponds to a regional postal division spanning multiple assembly constituencies. Precise constituency identification requires street address or coordinate input."`
    - **Zero arbitrary AC assignment occurs.**
- **Case C — Curated Provisional Linkage:**
  - Where an explicit curated reference exists (e.g., `500001` -> Nampally AC 61):
    - Resolves via canonical `stateData.getConstituency` (Case D).
    - Sets `coverageLevel: 'CURATED_PROVISIONAL_POINT'`.
    - Enforces `isScenarioEstimate: true` and attaches spatial caveat on `impactAnalysis`.
    - Labels `proposedConstituency` as a scenario projection.
- **Case D — Canonical Service Reuse:**
  - All constituency metadata is retrieved from `stateData.getConstituency` or `stateData.getConstituencies`. No duplicate lookup or mock database is introduced.
