## 1. Executive Summary & Objective

CTO Directive 082 resolves the error classification ambiguity identified in Directive 081: in `scripts/generate_checksum_manifest.mjs`, error codes `EPERM` and `EBADF` were included unconditionally in `UNSUPPORTED_DIR_SYNC_CODES` as benign, non-fatal unsupported operations. This introduced the risk of treating critical descriptor corruption (`EBADF`) or POSIX security and permission faults (`EPERM`) as harmless filesystem capability limitations, thereby masking genuine durability uncertainty.

Directive 082 establishes a rigorous, platform-specific error classification taxonomy and completes all requirements:
1. **Narrowed POSIX Capability Refusal Set:** Standardizes documented POSIX filesystem capability refusal codes strictly to `EINVAL`, `ENOTSUP`, `EOPNOTSUPP`, and `EISDIR`.
2. **Fail-Closed Descriptor Protection (`EBADF`):** `EBADF` represents an invalid, unopened, or corrupted file descriptor. It is an abnormal runtime failure and must fail closed with `PostRenameDurabilityError` across all platforms.
3. **Narrowly Justified Platform-Specific `EPERM` Handling:**
   - **POSIX (Linux, macOS, BSD):** `EPERM` indicates a permission denial, capability shortfall (e.g. lack of `CAP_SYS_ADMIN`), or security sandbox restriction. It is NOT an unsupported filesystem capability and fails closed with `PostRenameDurabilityError`.
   - **Windows (`win32`):** When Node.js/libuv attempts to flush a directory handle via Win32 `FlushFileBuffers`, Windows returns Win32 error code 5 (`ERROR_ACCESS_DENIED`), which libuv translates to `EPERM`. In this narrowly justified platform context, `EPERM` is recognized as the Win32 directory handle flush limitation and classified as non-fatal `SKIPPED_PLATFORM_WIN32_EPERM`.
4. **Honest Durability State Taxonomy:** Distinguishes 4 explicit durability states:
   - `CONFIRMED_SYNCHRONIZATION`: Directory metadata flush succeeded and was confirmed to stable storage (`directorySynced: true`).
   - `EXPLICITLY_UNSUPPORTED_<CODE>`: Underlying filesystem returned a standard POSIX capability refusal code (`directorySynced: false`).
   - `SKIPPED_PLATFORM_WIN32` / `SKIPPED_PLATFORM_WIN32_EPERM`: Directory flush was skipped or rejected due to documented Win32 handle limitations (`directorySynced: false`).
   - `UNCONFIRMED_DURABILITY_ERROR`: Genuine I/O error or permission fault triggering `PostRenameDurabilityError`.
5. **Anti-Rollback & Preserved Replacement Guarantee:** Preserves the newly installed manifest on disk after rename succeeds without attempting destructive rollback or falsely claiming the previous manifest remains intact.
6. **Suppression of Unqualified Success Banners:** Ensures `MANIFEST GENERATION: 100% COMPLETE` is never emitted when directory durability confirmation fails.
7. **Regression Test Battery Expansion:** Expands `scripts/tests/generate_checksum_manifest.test.mjs` from 26 to 32 tests, covering every error classification path, platform branch, descriptor corruption, and fault injection mode.
8. **Hardened Mechanical Accounting:** Updates `scripts/audit_artifact_accounting.mjs` with Category P (`P_DIRECTIVE_082`), reconciling total deliverables to 54 across 16 categories, and verifying git provenance coordinates for Directive 081.

## 2. Technical Architecture & Implementation Details

### 2.1 Error Classification Taxonomy

The error classification logic is decoupled into a pure, standalone function `classifyDirectorySyncError(dirErr, platform)` in `scripts/generate_checksum_manifest.mjs`:

```javascript
export const POSIX_UNSUPPORTED_DIR_SYNC_CODES = new Set([
  'EINVAL',
  'ENOTSUP',
  'EOPNOTSUPP',
  'EISDIR'
]);

export function classifyDirectorySyncError(dirErr, platform = process.platform) {
  const code = dirErr && dirErr.code ? String(dirErr.code).toUpperCase() : 'UNKNOWN';

  // 1. Standard POSIX filesystem capability refusal codes
  if (POSIX_UNSUPPORTED_DIR_SYNC_CODES.has(code)) {
    return {
      isFatal: false,
      status: `EXPLICITLY_UNSUPPORTED_${code}`,
      reason: `Filesystem capability refusal: directory synchronization is explicitly unsupported (${code})`
    };
  }

  // 2. Platform-specific Windows EPERM handling (Win32 FlushFileBuffers on directory handles)
  if (code === 'EPERM' && platform === 'win32') {
    return {
      isFatal: false,
      status: 'SKIPPED_PLATFORM_WIN32_EPERM',
      reason: 'Win32 FlushFileBuffers unsupported on directory handle (ERROR_ACCESS_DENIED / EPERM)'
    };
  }

  // 3. EBADF is fatal on all platforms (bad/corrupted file descriptor)
  if (code === 'EBADF') {
    return {
      isFatal: true,
      status: 'UNCONFIRMED_DURABILITY_ERROR',
      reason: 'Invalid or corrupted directory file descriptor (EBADF)'
    };
  }

  // 4. POSIX EPERM is fatal (permission/sandbox failure)
  if (code === 'EPERM') {
    return {
      isFatal: true,
      status: 'UNCONFIRMED_DURABILITY_ERROR',
      reason: 'Operation not permitted on POSIX directory (EPERM)'
    };
  }

  // 5. Genuine filesystem or I/O failure (EIO, ENOSPC, EROFS, EACCES, etc.)
  return {
    isFatal: true,
    status: 'UNCONFIRMED_DURABILITY_ERROR',
    reason: `Genuine filesystem or I/O error during directory synchronization (${code})`
  };
}
```

### 2.3 Post-Rename Point-of-No-Return Invariant

Under Directive 082:
1. **Pre-Rename Failure:** If an error occurs during open, write, file `fsync`, or rename, the temporary file is unlinked, and the original target manifest is preserved 100% byte-for-byte.
2. **Post-Rename Failure:** If directory synchronization fails after rename succeeds:
   - The new manifest has already replaced the old manifest at `targetPath`.
   - The function preserves `targetPath` and does NOT attempt an unsafe rollback or deletion.
   - It throws `PostRenameDurabilityError`, which explicitly informs the caller that the new manifest is installed on disk, but directory-entry durability could not be verified to stable storage.
   - It explicitly clarifies: `The previous manifest was replaced and is no longer intact`.
