### 2.2 Provenance Basis: Distinguishing Missingness from Genuine Zeros

In strict compliance with Directive 027, missingness was not inferred from numeric zero alone:
1. **Underlying Source Code Provenance:**
   In `scripts/generate-b2-2e-forensic-manifests.mjs`, each seed profile object in `data/seed/` is extracted as an AST text block.
   - **Missing Disclosure:** If the source object completely lacks the `totalAssets:` or `totalLiabilities:` key (e.g. `hasAssets === false` or `hasLiab === false`), `assetsM` or `liabM` evaluates to `null`. In the original unhardened pipeline, `${a.total_liabilities || 0}` coerced this absence into an artificial `0`.
   - **Genuine Disclosed Zero:** If the source object contains `totalAssets: 0` or `totalLiabilities: 0`, the regex `\btotalAssets:\s*(\d+)` matches `0`. This candidate explicitly declared zero assets or zero debt on EC Form 26.
2. **Automated Regression Proof:**
   This distinction is formally tested and verified in `tests/generator-b2-2e-ingestion.test.mjs`:
   - TEST 02 verifies that missing keys remain `null`, never defaulting to 0.
   - TEST 03 verifies that explicit zeros remain `0`.

## 3. Workstream B — Database Schema Feasibility Findings

We conducted an offline inspection of the database schema across `supabase/migrations/008_election_affidavits.sql`, `050_political_entity_model.sql`, and `066_downstream_civic_extensions.sql`.

### 3.1 `total_liabilities` Nullability & Feasibility
- **Schema Definition (Migration 008, Line 29):**
  ```sql
  total_liabilities BIGINT DEFAULT 0,
  ```
- **Nullability Analysis:**
  The column does NOT specify `NOT NULL`. In PostgreSQL, any column without `NOT NULL` is **NULLABLE**.
- **Constraint Audit:**
  Zero check constraints, table constraints, foreign keys, or triggers prohibit `NULL` on `total_liabilities`.
- **Stored Representation:**
  PostgreSQL stores `NULL` natively in a 1-bit null bitmap. Storing `NULL` for `total_liabilities` is 100% supported by the PostgreSQL engine.
- **Application Consumers:**
  Neither `apps/api/` nor `apps/mobile/` enforces non-null assertions on `total_liabilities`. In `apps/mobile/lib/stateDataDispatcher.refactored.ts`, `totalLiabilities: row.total_liabilities` passes through `number | null | undefined` without error.

---

### 3.2 `total_assets` Generated Column Semantics
- **Schema Definition (Migration 008, Lines 24–26):**
  ```sql
  total_assets BIGINT GENERATED ALWAYS AS (
    self_movable_assets + self_immovable_assets + spouse_movable_assets + spouse_immovable_assets
  ) STORED,
  ```
- **Generated Column Behavior:**
  PostgreSQL `GENERATED ALWAYS ... STORED` columns **CANNOT be inserted or updated directly**. Attempting an explicit write triggers PostgreSQL error `42601`: `ERROR: cannot insert/update into generated column "total_assets"`.
- **Why Stored Values Are Currently 0:**
  The B2.2-E SQL chunk INSERT column lists do not include `self_movable_assets`, `self_immovable_assets`, `spouse_movable_assets`, or `spouse_immovable_assets`. Because they are omitted, PostgreSQL assigns them their column default `DEFAULT 0`. The generated expression calculates $0 + 0 + 0 + 0 = 0$.
- **Database Correction Feasibility for Assets:**
  To make `total_assets` evaluate to `NULL` in PostgreSQL, all four component columns must be set to `NULL` (since `NULL + NULL + ...` evaluates to `NULL`). Writing directly to `total_assets` is impossible.
- **Conclusion:**
  No schema changes are authorized. In PostgreSQL, `total_assets` will continue to evaluate to `0` until individual component assets are modeled in a future schema evolution.
