## 3. Production-Path Adversarial Testing Architecture (§2)

To eliminate ad-hoc test-internal checks and ensure tests evaluate actual production code, reusable validation logic was extracted into `scripts/adjudication_validators.mjs`. The test suite `scripts/tests/adjudication_manifest.test.mjs` was re-architected to invoke these functions directly across seven distinct production failure paths:

### 3.1 Production Validation Functions (`scripts/adjudication_validators.mjs`)

1. `validateCrosswalk(crosswalkList, expectedPopulation)`: Validates exact size, array structure, unique manifest IDs, unique target UUIDs, UUID v4 format, and constructs bidirectional lookup maps. Throws `CROSSWALK_POPULATION_MISMATCH`, `DUPLICATE_CROSSWALK_MANIFEST_ID`, `DUPLICATE_CROSSWALK_TARGET_UUID`, or `MALFORMED_CROSSWALK_ENTRY`.
2. `validateSqlChunks(chunkFiles, crosswalkTargetUuidSet, repoRoot)`: Parses raw SQL `INSERT INTO candidate_affidavits` statement tuples, verifies tuple counts, extracts target UUIDs and column 12 liability values, asserts uniqueness, and validates bidirectional correspondence with crosswalk targets. Throws `CHUNK_FILE_NOT_FOUND`, `CHUNK_TUPLE_COUNT_MISMATCH`, `DUPLICATE_SQL_CHUNK_UUID`, `ORPHAN_SQL_CHUNK_UUID`, or `CROSSWALK_UUID_MISSING_IN_SQL`.
3. `validateEligibilityGate({ eligibility, passesExistingOfflineVerifier, expectedDatabaseValue, proposedValue })`: Validates gate invariants. Throws `ILLEGAL_ELIGIBLE_STATE` if marked `ELIGIBLE` without `passesExistingOfflineVerifier === true`, or `ILLEGAL_INELIGIBLE_STATE` if marked `INELIGIBLE` when `expectedDatabaseValue !== proposedValue`.
4. `evaluateDimensionEligibility(...)`: Encapsulates full dimensional evaluation including `validateCorrectionEligibility()` invocation, expected database value determination, and verifier outcome mapping.
5. `validateSummaryReconciliation(manifest, summary)`: Asserts bit-for-bit reconciliation of all group counts, dimensional totals, and eligibility classifications between row-level manifest entries and summary totals. Throws `SUMMARY_RECONCILIATION_MISMATCH`.
6. `validateSourceEvidenceFile(relPath, expectedSha256, repoRoot)`: Asserts source file existence and bitwise SHA-256 integrity. Throws `MISSING_SOURCE_FILE` or `SOURCE_HASH_MISMATCH`.

## 5. Verifier Input Semantics Clarification (§4)

In `scripts/verify_financial_remediation.mjs`, `validateCorrectionEligibility()` enforces Pre-condition 3:
```javascript
if (correction.currentRepresentedValue !== manifestRecord.total_assets) {
  throw new Error(`Correction declares original value ${correction.currentRepresentedValue} differing from manifest value ${manifestRecord.total_assets}`);
}
```
This requires that the `correction` object passed to the verifier declare the baseline value recorded in the Form 26 affidavit manifest (`manifestRecord.total_assets`). 

Directive 073 eliminates previous ambiguity between the Form 26 manifest baseline and the expected database storage representation by establishing two explicit fields in every row of `reports/w021_5_financial_remediation_adjudication_manifest.json`:
- `manifestBaselineValue`: The authoritative Form 26 manifest disclosure value (`aff.total_assets` for assets; `null` if in missing inventory, `aff.total_liabilities` otherwise). Passed to the verifier as `correction.currentRepresentedValue`.
- `expectedDatabaseValue`: The offline expectation of what is stored in the database (`0` for assets due to schema generated column defaults; column 12 tuple value from SQL chunks for liabilities).

This separation guarantees full compliance with verifier Pre-condition 3 without conflating manifest baseline disclosures with offline database representations.
